## 0. Как работать с этим документом

1. Фазы по порядку: Фаза 1 → 2 → 3. Внутри фазы порядок шагов значим.
2. Один шаг = один атомарный коммит (`fix(N.M): …`), сообщение ссылается на
   номер шага.
3. После каждого шага: `BOT_TOKEN=test-token python -m pytest -q` — зелено.
4. Для каждого бага Фаз 1–2 — регрессионный тест, который **падает до фикса
   и проходит после**. Проверь это явно.
5. Новые строки интерфейса — сразу в `ru/en/es` (`test_l10n_key_coverage.py`).
6. Миграции — только мягкие (`ALTER TABLE ADD COLUMN` в `try/except
   OperationalError`, `bot/database/engine.py`). Alembic не вводить.

### Инварианты — не трогать

- **Naive UTC в БД**, конвертация в локальное время только при рендере.
- **Anti-drift снуза привычек**: у habit-like recurring `execution_time`
  при снузе не перезаписывается (якорь rrule).
- **`completed_for_execution_time`** — механизм скрытия выполненного цикла,
  не заменять на проверку `status`.

# Фаза 1 — Безопасность и доступность

## Шаг 1.1. Веб-сервер слушает `0.0.0.0` и стартует безусловно

**Проблема.** `bot/config.py:60` — `WEB_SERVER_HOST: str = "0.0.0.0"`, и
`bot/__main__.py:197-198` поднимает сервер **всегда**, без флага включения:

```python
web_app = create_app(session_pool, bot_token=config.BOT_TOKEN.get_secret_value())
web_runner = await start_web_server(web_app, config.WEB_SERVER_HOST, config.WEB_SERVER_PORT)
```

Любая существующая установка после обновления начинает слушать порт 8080 на
**всех интерфейсах** — без TLS, — хотя владелец мог не хотеть ни ICS-фида,
ни Mini App. В `docker-compose.yml` секции `ports:` нет, поэтому в Docker
наружу порт не публикуется — но при запуске из venv (см. `running_guide.md`,
`DEPLOYMENT.md`) он открыт всей локальной сети. `0.0.0.0` — неверный дефолт
для сервиса, перед которым по замыслу должен стоять реверс-прокси.

**Что сделать.**
1. `bot/config.py`: сменить дефолт `WEB_SERVER_HOST` на `"127.0.0.1"`.
   В комментарии рядом объяснить: наружу порт выставляет реверс-прокси,
   менять на `0.0.0.0` осмысленно только внутри контейнера.
2. Добавить `WEB_SERVER_ENABLED: bool = False`. В `bot/__main__.py`
   поднимать сервер и вызывать `web_runner.cleanup()` только под этим
   флагом. Логировать на старте, включён он или нет.
3. `DEPLOYMENT.md`: раздел про то, что нужно выставить, чтобы §4.4/§4.6
   заработали (`WEB_SERVER_ENABLED`, `PUBLIC_BASE_URL`, `MINI_APP_URL`,
   реверс-прокси с TLS, публикация порта в compose).

**Проверка.** Тест: при `WEB_SERVER_ENABLED=False` в приложении нет
HTTP-сокета (или, проще на уровне юнита, — фабрика сервера не вызывается).

## Шаг 1.2. `initData`: поле `signature` и HMAC-проверка

**Проблема.** `bot/services/miniapp.py:66` строит data-check-string из всех
полей, кроме `hash`:

```python
data_check_string = "\n".join(f"{k}={v}" for k, v in sorted(data.items()))
```

Начиная с Bot API 7.10 Telegram кладёт в `initData` ещё и поле `signature`
(Ed25519, для сторонней валидации). Официальная документация раздела
«Validating data received via the Mini App» говорит про «все полученные
поля», а исключение `signature` названо явно **только** в соседнем разделе
про третью сторону («except _hash_ and _signature_»). Формулировка
неоднозначная, а цена ошибки максимальная: если `signature` из подсчёта
надо исключать, а мы его включаем, то HMAC не сойдётся **никогда и ни у
кого** — Mini App вернёт 401 всем пользователям. Текущие тесты этого не
ловят: они конструируют `initData` сами, тем же кодом, без `signature`.

**Что сделать.** Не чинить руками — перейти на валидатор из aiogram,
который уже есть в зависимостях и поддерживается вместе с Bot API:

1. Заменить тело `validate_init_data` на обёртку над
   `aiogram.utils.web_app.safe_parse_webapp_init_data(token=..., init_data=...)`,
   сохранив текущий контракт функции (возврат `{"user_id", "user",
   "auth_date"}` либо `None`, никаких исключений наружу).
2. Оставить собственную проверку свежести `auth_date` (окно и допуск на
   рассинхрон часов), если aiogram не покрывает её так же строго.
3. Добавить тест с **реальной** строкой `initData`, содержащей поле
   `signature`, и валидным `hash` — зафиксировать, что она принимается.

**Проверка.** Существующие тесты `bot/services/test_miniapp.py` остаются
зелёными; новый тест с `signature` падает на текущей реализации.

## Шаг 1.3. Теги без ограничений ломают меню тегов

**Проблема.** `bot/utils/tags.py:16` — `_TAG_RE = re.compile(r"#(\w+)")`:
ни длина тега, ни их количество ничем не ограничены. При этом
`bot/keyboards/inline.py:606` кладёт тег прямо в callback_data:

```python
InlineKeyboardButton(text=f"#{tag}", callback_data=f"tasks_tag:{tag}")
```

Telegram ограничивает `callback_data` **64 байтами**. Кириллица — 2 байта
на символ, значит тег длиннее ~28 кириллических букв уже переполняет лимит,
и aiogram/Telegram отвергает **всю клавиатуру** — экран тегов перестаёт
открываться, и починить это из интерфейса нельзя. Отдельно: число тегов не
ограничено, а `get_tags_menu_keyboard` рисует по кнопке на тег — полсотни
разных тегов дают клавиатуру, которую Telegram не примет. Ср. комментарий
`bot/handlers/reminders.py:68`, где этот же лимит уже осознан для задач.

**Что сделать.**
1. В `extract_tags_and_priority`: ограничить длину одного тега
   (например, 24 символа — режется, не отбрасывается) и их число на задачу
   (например, 10). Константы вынести рядом с `_TAG_RE`.
2. В `get_tags_menu_keyboard`: ограничить число кнопок (например, 30
   самых частых или первых по алфавиту) и, если тег всё же не влезает в
   64 байта в UTF-8, — не рисовать для него кнопку (или адресовать тег
   индексом, а не значением).
3. Проверить симметрично разбор `tasks_tag:` — он должен переживать
   отсутствующий/усечённый тег без исключения.

**Проверка.** Тесты: тег из 200 кириллических символов → в БД сохранён
усечённым, `callback_data` каждой кнопки ≤ 64 байт в UTF-8; 100 разных
тегов → клавиатура строится и число кнопок ограничено.

# Фаза 2 — Корректность

## Шаг 2.1. Экспорт данных не содержит теги и приоритет

**Проблема.** `bot/handlers/settings.py:200-222` перечисляет поля
напоминания вручную. Экспорт написан в §3.3, а `tags` и `priority`
появились позже, в §4.3, — и в payload их не добавили. «Забери свои
данные» молча отдаёт неполные данные, теряя ровно то, что пользователь
проставил руками.

**Что сделать.** Добавить `"tags": r.tags` и `"priority": r.priority` в
словарь напоминания в `build_data_export`.

**Проверка.** Тест: задача с тегом и приоритетом → оба поля присутствуют в
экспортированном JSON.

## Шаг 2.2. Неэкранированные шаблоны LIKE в поиске и фильтре по тегу

**Проблема.** `bot/database/dao/reminder.py:636` и `:612`:

```python
needle = f"%{query.strip()}%"
... Reminder.reminder_text.ilike(needle)
```

Пользовательский ввод попадает в шаблон LIKE как есть. Это **не** SQL-
инъекция (запрос параметризован), но `%` и `_` в тексте запроса работают
как подстановочные знаки: поиск «скидка 50%» находит не то, а запрос из
одного `%` матчит всю таблицу. Для фильтра по тегу результат в итоге
корректен (есть точная проверка на стороне Python, `:629`), но скан всё
равно расширяется до всей таблицы пользователя.

**Что сделать.** Экранировать `%`, `_` и сам символ экранирования в
`needle`, передавая `escape="\\"` в `ilike(...)`. Сделать это в обоих
местах (и в любом новом поиске по LIKE).

**Проверка.** Тест: задача «скидка 50%» и задача «скидка 500 рублей»;
`/find 50%` находит первую и не находит вторую. Тест: `/find %` не
возвращает всё подряд.

## Шаг 2.3. Молчаливое усечение результатов до 25

**Проблема.** `bot/handlers/reminders.py:1383` рендерит
`tasks[:_TASKS_PAGE_SIZE]`, а `bot/keyboards/inline.py:591` — `tasks[:25]`.
Обрезка правильная (иначе упрёмся в лимиты Telegram), но пользователю не
сообщается, что совпадений было больше: он видит 25 строк и делает вывод,
что это всё. Для поиска это хуже, чем для списка, — там хотя бы есть
пагинация.

**Что сделать.** Если `len(tasks) > _TASKS_PAGE_SIZE`, добавлять в конец
текста строку вида «показаны первые 25 из N» (ключ в ru/en/es).

**Проверка.** Тест: 40 совпадений → в тексте есть маркер усечения и ровно
25 строк задач; 10 совпадений → маркера нет.

## Шаг 2.4. `pre_checkout_query` без фильтра

**Проблема.** `bot/handlers/donate.py:76` — `@router.pre_checkout_query()`
без единого фильтра, обработчик безусловно отвечает `ok=True`. Сейчас это
верно (единственный платёжный поток — донат с фиксированной ценой), но
хендлер перехватывает **любой** pre-checkout бота: первый же будущий
платный поток окажется автоматически подтверждён, ничего не проверив.

**Что сделать.** Ограничить хендлер своим payload'ом (он уже задаётся —
`payload=f"donate:{amount}"`, `donate.py:66`): фильтровать по
`F.invoice_payload.startswith("donate:")`. Чужой pre-checkout — отклонять
явно, с сообщением об ошибке.

**Проверка.** Тест: pre-checkout с payload `donate:50` подтверждается;
с payload `something_else` — нет.

# Фаза 3 — Долг и производительность

## Шаг 3.1. HTTP-эндпоинты вне rate-limit

**Проблема.** `RateLimitMiddleware` (`bot/middlewares/rate_limit.py:25`)
защищает только апдейты Telegram. Новые HTTP-маршруты не прикрыты ничем.
`handle_ics_feed` (`bot/services/webserver.py:43-64`) на **каждый**
запрос — включая запрос с неверным токеном — открывает сессию БД и делает
SELECT, то есть неаутентифицированный трафик напрямую нагружает базу.
Подбор самого токена нереалистичен (`secrets.token_urlsafe(24)` — 192 бита),
речь именно о нагрузке.

**Что сделать.** Простой in-process лимит по IP для `/ics/` и
`/api/miniapp/*` (тот же подход, что в `RateLimitMiddleware`: окно +
счётчик, с обязательной очисткой протухших записей — утечка в этом месте
уже была и чинилась в §3.1 прошлой итерации). Для `/api/miniapp/*` сначала
проверять `initData`, потом ходить в БД.

**Проверка.** Тест через `aiohttp.test_utils`: N+1-й запрос за окно
получает 429.

## Шаг 3.2. `/api/miniapp/scores` — N+1 и выборка без границы

**Проблема.** `bot/services/webserver.py:121-125` в цикле по привычкам
дёргает `get_events_for_reminder(habit.id)` — отдельный запрос на каждую
привычку. Сам метод (`bot/database/dao/habit_event.py:125-134`) выбирает
**всю** историю событий привычки без ограничения по датам. У пользователя
с 20 привычками и парой лет истории это 20 запросов и десятки тысяч строк
в память на один HTTP-запрос.

**Что сделать.** Один запрос на всё: выбрать события всех привычек
пользователя разом (`WHERE reminder_id IN (...)`, сортировка по
`reminder_id, local_date, id`) и сгруппировать в Python. Ограничить окно
по датам тем, что реально нужно EMA-счёту (см. `compute_habit_score`,
`bot/services/habit_reports.py`), — если хвост старше окна на результат не
влияет, не читать его.

**Проверка.** Тест: 5 привычек → ровно один SELECT к `habit_events`
(считать через счётчик обращений или `sqlalchemy` event hook), значения
score не изменились.

## Шаг 3.3. Порог 25 продублирован

**Проблема.** `_TASKS_PAGE_SIZE = 25` живёт в
`bot/handlers/reminders.py:73`, а `bot/keyboards/inline.py:591` независимо
режет `tasks[:25]` числом. Две константы обязаны совпадать, но ничто этого
не гарантирует: разойдутся — текст и клавиатура покажут разные наборы.

**Что сделать.** Одна константа в одном месте (или в `inline.py`, откуда
её импортирует хендлер, или в общем модуле констант), оба среза — от неё.

**Проверка.** Достаточно существующих тестов; убедиться, что смена
константы меняет и текст, и клавиатуру согласованно.
