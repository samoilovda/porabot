# План доработки Porabot, итерация 5 — инструкция для ИИ-агента

Результат аудита `main` на коммите `04d05dd` (сразу после мерджа
`claude/habit-tracker-timezone-migration-xijjwb`).

В отличие от итерации 4, которая смотрела точечно на новый код §3/§4/§5,
этот аудит — сплошной обход всей кодовой базы: композиционный корень,
планировщик, пять минутных cron-джобов, DAO, хендлеры, веб-сервер,
парсер, инфраструктура и тесты. Поэтому здесь больше **структурных**
находок, чем точечных багов: сами по себе баги проекта немногочисленны и
локальны, а вот способ, которым проект растёт (минутный джоб на каждую
новую фоновую функцию, 2300-строчный `reminders.py`, in-memory FSM,
ручные soft-миграции), уже упирается в потолок.

**Базовая линия:** `BOT_TOKEN=test-token python -m pytest -q` → `360 passed`.
Ни один шаг этого плана не должен их ломать.

## 0. Как работать с этим документом

1. Фазы по порядку: Фаза 1 → 2 → 3 → 4. Внутри фазы порядок шагов значим.
2. Один шаг = один атомарный коммит (`fix(N.M): …` / `refactor(N.M): …`),
   сообщение ссылается на номер шага.
3. После каждого шага: `BOT_TOKEN=test-token python -m pytest -q` — зелено.
4. Для каждого бага Фаз 1–2 — регрессионный тест, который **падает до
   фикса и проходит после**. Проверь это явно, а не на глаз.
5. Новые строки интерфейса — сразу в `ru/en/es`
   (`bot/services/test_l10n_key_coverage.py` это проверяет).
6. Миграции схемы — по-прежнему мягкие
   (`_add_column_if_missing` в `bot/database/engine.py`). Alembic не
   вводить: разбор в шаге 4.3 объясняет, почему это осознанный отказ, а
   не забывчивость.

### Инварианты — не трогать

- **Naive UTC в БД**, конвертация в локальное время только при рендере.
- **Anti-drift снуза привычек**: у habit-like recurring `execution_time`
  при снузе не перезаписывается (это якорь rrule).
- **`completed_for_execution_time`** — механизм скрытия выполненного
  цикла recurring-задачи; не заменять проверкой `status`.
- **`pending_delete_at`** — soft-delete: каждый запрос активных
  напоминаний обязан его исключать.
- **`get_owned(reminder_id, user_id)`** — единственный способ достать
  напоминание по id из `callback_data`. Проверено: нарушений нет.

# Фаза 1 — Баги, которые видит пользователь

## Шаг 1.1. FSM-состояние живёт в памяти процесса

**Проблема.** `bot/__main__.py:138` — `dp = Dispatcher()`. Без явного
`storage=` aiogram подставляет `MemoryStorage`. При этом
`docker-compose.yml` объявляет `restart: always`, а деплой — это
`docker compose up -d --build`, то есть пересоздание контейнера.

Последствие: любой пользователь, находящийся в середине мастера
(`ReminderWizard.choosing_time`, `waiting_for_nag_limit`,
`SettingsState.waiting_for_timezone`, `HabitState.waiting_for_time` …),
после деплоя теряет состояние молча. Он отвечает на вопрос бота, попадает
в `StateFilter(None)` и его ответ (например, «`23:00`») уходит в
`handle_task_text` и превращается в **новую задачу «23:00»**. Это не
теоретическая деградация: `state.update_data(edit_reminder_id=...)`
хранит идентификатор редактируемого напоминания, и после рестарта правка
превращается в создание.

**Что сделать.**

1. Завести хранилище FSM на том же SQLite/БД, что и остальное состояние,
   либо (проще и достаточно) — на отдельном файле рядом с `jobs.sqlite`.
   Минимальный вариант без новых зависимостей: реализовать
   `BaseStorage` поверх таблицы `fsm_state(chat_id, user_id, state, data,
   updated_at)` в основной БД, регистрировать её через
   `_add_column_if_missing`-подобную мягкую миграцию (таблица создаётся
   через `Base.metadata.create_all`).
2. Передать storage в `Dispatcher(storage=...)`.
3. Добавить в `bot/__main__.py` периодическую очистку записей старше
   суток (по образцу `cleanup_stale_timers`) — состояние мастера не
   должно жить вечно.

**Тест.** `bot/services/test_fsm_storage_survives_restart.py`: записать
состояние через один экземпляр storage, создать второй поверх той же БД,
убедиться, что `get_state`/`get_data` возвращают то же самое.

## Шаг 1.2. Нет глобального обработчика ошибок

**Проблема.** Ни в `bot/__main__.py`, ни в роутерах нет `@dp.errors`.
Любое исключение, не пойманное внутри хендлера, всплывает в aiogram,
логируется — и **пользователь не получает ничего**. Для колбэка это
особенно плохо: Telegram показывает «часики» на кнопке до таймаута,
потому что `callback.answer()` так и не вызвали.

Мест, где это реально достижимо, много: `callback_show_completed`
(шаг 1.5) падает на длинном сообщении; `callback_edit_edit` при
`int(callback.data.split(...))` на подделанном `callback_data`;
`state_habit_time` при `hhmm.split(":")` и т. д.

**Что сделать.**

1. Зарегистрировать `@dp.errors` в композиционном корне: залогировать с
   `exc_info`, затем — если событие это `CallbackQuery`, обязательно
   `answer(l10n["generic_error"], show_alert=True)`; если `Message` —
   `answer(l10n["generic_error"])`. Обе ветки сами обёрнуты в
   `try/except`, чтобы обработчик ошибок не стал источником ошибок.
2. Ключ `generic_error` — в `ru/en/es`.
3. `DatabaseMiddleware` уже делает `rollback` на исключении и
   пробрасывает дальше — порядок с `dp.errors` совместим, ничего менять
   не надо.

**Тест.** `test_error_handler_answers_callback.py`: хендлер, кидающий
`RuntimeError`, прогнанный через диспетчер, приводит к вызову
`callback.answer` с alert.

## Шаг 1.3. `pytz` + `replace()` + `timedelta` — сдвиг на час около DST

**Проблема.** В коде уже описана правильная схема — см. подробный
комментарий в `SchedulerService._next_quiet_end_utc`
(`bot/services/scheduler.py`): у `pytz` объект, полученный из
`datetime.now(tz)`, несёт **зафиксированное** смещение на текущую дату;
`replace(hour=…)` его сохраняет, `+ timedelta(days=1)` тоже. Если
кандидат перепрыгивает переход на летнее/зимнее время, результат уезжает
на час. Правильно — считать в наивном локальном времени и потом
`tz.localize(...)`.

Схема исправлена в `_next_quiet_end_utc` и в `next_occurrence_utc`, но
**осталась в четырёх местах**:

| Файл | Строка | Что ломается |
|---|---|---|
| `bot/keyboards/inline.py` | 89 | Кнопки «утро/день/вечер/ночь» — в `callback_data` зашивается неверный ISO-момент |
| `bot/handlers/reminders.py` | 647 | «Завтра в 9:00» |
| `bot/handlers/reminders.py` | 2247 | Снуз «утро/день/вечер/ночь» |
| `bot/handlers/habits.py` | 113 | `_schedule_fluid_habit_for_today` — ручное время для fluid-привычки |

**Что сделать.**

1. Завести в `bot/utils/time_ext.py` одну функцию:
   ```python
   def local_time_today_or_tomorrow(tz_str: str, hour: int, minute: int = 0,
                                    *, now_utc: datetime | None = None) -> datetime:
       """Ближайшее локальное HH:MM (сегодня или завтра), как aware-UTC.
       DST-корректно: арифметика в наивном локальном времени, затем localize."""
   ```
   плюс вариант «строго сегодня, иначе ValueError» для fluid-привычки
   (там прошедшее время — это ошибка ввода, а не повод переносить).
2. Переписать все четыре места через неё. Никакого `replace()` по
   aware-datetime в проекте остаться не должно.
3. Добавить в `bot/services/test_dst_*` (или новый файл) регрессию:
   `Europe/Moscow` не подойдёт (нет DST) — брать `America/New_York` или
   `Europe/Berlin` и точку за несколько часов до перехода.

**Тест.** `test_dst_time_slot_helpers.py`: для `Europe/Berlin` в ночь
перехода «вечер 19:00» даёт локальные 19:00, а не 18:00/20:00.

## Шаг 1.4. Миграция часового пояса может выстрелить в прошлое

**Проблема.** `bot/services/tz_migration.py::apply_migration` пересчитывает
`execution_time`, сохраняя локальное время суток, и сразу вызывает
`schedule_reminder`. Но `new_execution_time_utc` **не проверяется на
«в будущем»**. Сдвиг может быть до ±14 часов: привычка, до которой
оставалось 2 часа, при переезде на пояс восточнее получает
`execution_time` на 3 часа в прошлом. `job_defaults` содержит
`misfire_grace_time: 3600`, так что APScheduler такой job не отбросит, а
**выполнит немедленно** — пользователь получает уведомление о привычке
сразу после смены часового пояса, а `habit_active_due_at` уезжает на
цикл, которого не было.

**Что сделать.**

1. В `build_migration_plan` (или в `apply_migration` перед
   `schedule_reminder`) — если `new_execution_time_utc <= now_utc`, для
   recurring-привычки взять `next_occurrence_utc(rrule,
   new_execution_time_utc, new_tz, now_utc)`; для fluid — не мигрировать
   (положить в `kept`).
2. `habit_active_due_at` сдвигать тем же `delta`, что и сейчас, но
   только когда миграция реально применена.
3. В сводке (`_render_tz_migration_summary`) показать перенесённые «на
   завтра» отдельной строкой, чтобы пользователь понимал, что сегодня
   сигнала не будет.

**Тест.** `test_tz_migration_never_fires_immediately.py`: привычка на
через 2 часа, переезд `Europe/Lisbon` → `Asia/Tokyo`; после миграции
`execution_time` строго в будущем и job запланирован не на «сейчас».

## Шаг 1.5. Неограниченные по длине сообщения

**Проблема.** Ограничение Telegram (4096 символов, ~100 кнопок) уже
аккуратно учтено в списке задач (`_paginate_tasks_for_list`), в брифах
(`_BRIEF_ITEMS_LIMIT` + `_LINE_PREVIEW_CHARS`) и в `/find`
(`find_truncated_notice`). Но три экрана остались без ограничения:

1. `bot/handlers/reminders.py:1710-1725`, `callback_show_completed` —
   строка на каждую задачу, завершённую за 7 дней, без среза. При
   `MAX_ACTIVE_REMINDERS = 200` и ежедневных повторяющихся задачах это
   легко перебирает 4096 символов. `edit_text` здесь **не обёрнут** в
   `try/except TelegramBadRequest` (в отличие от соседних мест), так что
   исключение улетает наверх — см. шаг 1.2.
2. `bot/handlers/habits.py::cb_habit_list` — строка и 1–2 кнопки на
   каждую привычку, при лимите `MAX_ACTIVE_HABITS = 50`.
3. `bot/services/habit_reports.py::_build_report_text` — строка на каждую
   привычку с событиями за неделю/месяц.

**Что сделать.**

1. Вынести срез в общий хелпер (в `bot/utils/` или переиспользовать
   `daily_briefs._limit_items`, подняв его в утилиты) — один механизм
   «показать N + строка „ещё M“» на весь проект.
2. Применить к трём местам выше; для завершённых задач — ещё и
   `_preview_line` по тексту, как в брифах.
3. Обернуть `edit_text` в `callback_show_completed` в
   `try/except TelegramBadRequest`, как в остальных колбэках.

**Тест.** `test_message_length_bounds.py`: 300 завершённых задач по 200
символов → отрендеренный текст ≤ 4096 и содержит строку «ещё N».

# Фаза 2 — Производительность, масштабируемость, целостность

## Шаг 2.1. N+1 в списке привычек

**Проблема.** `bot/handlers/habits.py:400`, внутри цикла по привычкам:

```python
habit_events = await habit_event_dao.get_events_for_reminder(h.id)
score = compute_habit_score(habit_events)
```

Это ровно тот баг, который уже чинили в Mini App (`fix(3.2)`): один
запрос на привычку, и каждый запрос тянет **всю историю событий без
границы по датам**. 50 привычек × N дней истории = 50 round-trip'ов и
несколько тысяч ORM-объектов на одно нажатие кнопки «Мои привычки».

**Что сделать.** Заменить на уже существующий батч-метод
`HabitEventDAO.get_events_for_reminders([h.id for h in habits])` — он был
добавлен ровно для этого. Плюс: убрать `from bot.services.habit_reports
import compute_habit_score` **из тела цикла** в шапку модуля.

**Тест.** По образцу `test_miniapp_scores_query_count.py` — счётчик
выполненных SELECT'ов не растёт с числом привычек.

## Шаг 2.2. N+1 в недельных и месячных отчётах

**Проблема.** `bot/services/habit_reports.py:180-186` и `208-214` —
dict-comprehension, вызывающий `get_events_for_reminder` на каждую
строку отчёта. Это происходит в минутном cron-джобе, для каждого
пользователя, у которого сегодня день отчёта.

**Что сделать.** Тот же `get_events_for_reminders`, один вызов на
пользователя, результат переиспользовать и для недельного, и для
месячного отчёта (они считаются в одном проходе).

**Тест.** Счётчик запросов на пользователя с 10 привычками — константа.

## Шаг 2.3. Пять минутных джобов с полным обходом пользователей

**Проблема.** Каждую минуту стартуют пять cron-джобов:

| Джоб | Файл | Кого перебирает |
|---|---|---|
| `daily_briefs_minutely` | `daily_briefs.py:544` | всех с `briefs_enabled` и активной задачей |
| `habit_sweeper` | `habit_sweeper.py:161` | всех с активной привычкой |
| `missed_task_recovery` | `missed_recovery.py:150` | **всех с `missed_recovery_enabled`** (по умолчанию `True` → фактически всех) |
| `habit_reports` | `habit_reports.py:329` | всех с привычками и включёнными отчётами |
| `delete_cleanup` | `delete_cleanup.py:76` | напоминания в окне удаления |

Каждый из них открывает **отдельную сессию на пользователя** и делает
несколько запросов внутри. Порядок работы за минуту — O(пользователи ×
константа) сессий к одному SQLite-файлу, который одновременно
обслуживает и хендлеры. При 1000 пользователей это ~4000 сессий в
минуту при том, что реальную работу делают единицы.

Существенно: 99 % итераций отсеиваются **уже после** загрузки
пользователя — сравнением `now_local.strftime("%H:%M") <
user.missed_recovery_time` в Python.

**Что сделать (не переписывая архитектуру, а сузив выборку).**

1. Ввести в `bot/services/` общий модуль `job_targets.py` с одной
   функцией: по текущему UTC-моменту вернуть множество имён таймзон, в
   которых локальное время сейчас попадает в интересующее окно. Зон,
   реально встречающихся в БД, немного (`SELECT DISTINCT timezone`), а
   индекс `idx_users_timezone` для этого уже есть.
2. Переписать выборку в каждом из четырёх «пользовательских» джобов на
   вид «пользователи, у которых (а) фича включена, (б) таймзона в
   вычисленном множестве, (в) дневной claim ещё не поставлен» — то есть
   перенести фильтр по времени и по `last_*_date` **в SQL**.
3. Обрабатывать отобранных пользователей **пачками** в одной сессии
   (например, по 50), а не по сессии на пользователя. Изоляция ошибок
   при этом сохраняется: `try/except` вокруг каждого пользователя с
   `savepoint` (`session.begin_nested()`), как уже сделано в
   `HabitEventDAO.record`.
4. `delete_cleanup` оставить как есть — он уже фильтрует в SQL.

**Тест.** `test_job_target_selection.py`: пользователь с
`morning_brief_time=09:00` в `Asia/Tokyo` попадает в выборку только в
соответствующую UTC-минуту; пользователь с уже проставленным
`last_morning_brief_date` не попадает вовсе (проверять через счётчик
загруженных `User`, а не через факт отправки).

## Шаг 2.4. Нет политики хранения данных

**Проблема.** `grep -rn "retention\|purge" bot/` не находит ничего.
Растут без ограничения:

- `habit_events` — одна строка на цикл привычки в день, навсегда.
  50 привычек × 365 дней = 18 250 строк на пользователя в год, и
  `get_events_for_reminder` читает их **целиком** при каждом расчёте
  EMA-скора (шаги 2.1/2.2).
- `reminders` со `status='completed'` — одноразовые задачи никогда не
  удаляются.
- Пользователи, заблокировавшие бота: `forbidden_strikes` доходит до 3,
  напоминания перестают планироваться, но строки остаются.

**Что сделать.**

1. Добавить джоб `retention_cleanup` с **суточным** (не минутным!)
   расписанием: `cron(hour=3, minute=17)`.
2. Правила (константы в модуле, чтобы менялись одним местом):
   - `habit_events` старше 400 дней — удалять;
   - `reminders` с `status='completed'` и `completed_at` старше 180 дней
     и `is_recurring=False` — удалять;
   - перед удалением события — убедиться, что оно не последнее для
     привычки (иначе EMA-скор новой привычки скакнёт).
3. Оценить влияние на `compute_habit_score`: EMA с `alpha=0.2` за 400
   дней вырождается ниже точности округления, влияния на показанный скор
   нет. Зафиксировать это тестом, а не рассуждением.
4. Задокументировать сроки в `BOT_OVERVIEW.md` — это пользовательские
   данные, срок хранения должен быть написан.

**Тест.** `test_retention_cleanup.py`: события старше порога исчезают,
свежие остаются, скор до и после чистки совпадает.

## Шаг 2.5. Двойная запись «БД + jobstore» без общей транзакции

**Проблема.** Планировщик пишет в `jobs.sqlite` (SQLAlchemyJobStore,
синхронный, коммитит немедленно), а данные — в `porabot.db` через
асинхронную сессию, которую коммитит `DatabaseMiddleware` **после**
возврата из хендлера. Между ними нет общей транзакции.

Код это частично компенсирует — почти каждый вызов `schedule_reminder`
обёрнут в `try/except` с `session.rollback()` и снятием job'а (см.
`_save_and_show_edit`, `_apply_repeat_change`, `callback_snooze_act`,
`callback_done_undo`, `apply_migration`). Но компенсация покрывает
только «job не создался». Обратный случай — job создался, а коммит
сессии упал уже **после** выхода из хендлера (в middleware) — не
покрыт ничем: остаётся job на напоминание с неактуальным или
несуществующим состоянием.

Смягчает ситуацию то, что `_execute_reminder` перечитывает напоминание
из БД по id и корректно обрабатывает «не найдено» и «уже выполнено». То
есть последствие — не потеря данных, а лишний холостой job и, в худшем
случае, срабатывание по старому времени.

**Что сделать (соразмерно риску — без outbox-таблицы).**

1. Сделать `reconcile_jobs_with_db` двусторонним: сейчас он только
   **добавляет** недостающие job'ы. Добавить вторую половину — снять
   job'ы, для которых нет соответствующей строки (или строка
   `completed` / `pending_delete_at` / `forbidden_strikes >= LIMIT`).
   Идентификаторы job'ов уже строго `str(id)` и `nag_{id}`, так что
   сопоставление тривиально.
2. Зарегистрировать этот же reconcile как периодический джоб (раз в
   час), а не только на старте.
3. Задокументировать в docstring `SchedulerService`, что jobstore —
   **производное** состояние от БД, а БД — источник истины. Сейчас это
   верно фактически, но нигде не сказано.

**Тест.** `test_reconcile_removes_orphan_jobs.py`: job для удалённой
строки снимается; job для `completed` снимается; job для валидной
строки не трогается.

## Шаг 3.3. CI без статических проверок

**Проблема.** `.github/workflows/deploy.yml` делает ровно две вещи:

3. Заменить `datetime.utcnow()` на `datetime.now(timezone.utc).replace(tzinfo=None)`

4. Добавить в workflow шаг `ruff check` **до** тестов, чтобы деплой не

## Шаг 3.4. Обходной путь установки в документации не работает

# Фаза 4 — Структурные решения (обсудить до реализации)

Эти пункты — не баги. Это места, где текущее устройство работает, но
делает каждое следующее изменение дороже. Ни один из них **не следует
делать «заодно»** с Фазами 1–3: каждый требует отдельного решения
владельца продукта.

## 4.1. `bot/handlers/reminders.py` — 2302 строки

Файл совмещает: мастер создания задачи, конструктор RRULE (~400 строк,
14 колбэков `rrb_*`), поиск и фильтры, пагинацию списка, отметку
«выполнено», вечерний wrap-up, снуз, заметки к выполнению и catch-all
для не-текстовых сообщений. Он же — последний роутер в цепочке, то есть
любой промах вышестоящего роутера попадает именно сюда.

**Предложение.** Разбить по границам, которые уже видны в коде (там даже
есть комментарии-разделители — они и есть будущие модули):

```
bot/handlers/reminders/
    __init__.py      # router = Router(); include_router(...) остальных
    wizard.py        # создание: текст → время → сохранение
    repeat.py        # конструктор RRULE (rrb_*)
    listing.py       # список, пагинация, /find, фильтры, теги
    completion.py    # done / undo / note / skip_next / wrap-up
    snooze.py        # снуз
```

Важно: **порядок регистрации сохранить точно** — catch-all
(`handle_task_text`, `handle_non_text_message`) обязан остаться
последним, иначе ломается вся маршрутизация. Есть тест
`test_menu_router_priority.py`, который это охраняет; расширить его до
проверки порядка внутри нового под-пакета.

Оценка: механический перенос без изменения логики, но большой diff.
Делать отдельной PR, ничего больше в неё не класть.

## 4.2. Глобальный синглтон `_instance`

`bot/services/scheduler.py` держит модульную переменную `_instance`,
которую `SchedulerService.__init__` присваивает как побочный эффект.
Все пять cron-джобов начинаются с `from bot.services.scheduler import
_instance` внутри тела функции и лезут через неё к `bot` и
`session_pool`.

Причина реальна: APScheduler сериализует job'ы, и целью job'а не может
быть bound-метод. Но следствия неприятны: порядок инициализации важен и
нигде не выражен; в тестах приходится подменять приватную переменную
модуля; две `SchedulerService` в одном процессе молча перезапишут друг
друга; `__init__` с побочным эффектом на модуль — источник неожиданностей.

**Предложение.** Ввести явный `AppContext` (dataclass: `bot`,
`session_pool`, `scheduler`), создаваемый в композиционном корне и
хранимый в **одном** модуле `bot/context.py` с функциями
`set_context()` / `get_context()`, где `get_context()` кидает понятную
ошибку, если контекст не установлен. Это тот же синглтон, но
именованный, тестируемый и с одной точкой входа вместо импорта приватной
переменной из чужого модуля.

## 4.3. Схема и миграции разъехались

`bot/database/engine.py::init_db` содержит два списка `ALTER TABLE ADD
COLUMN` — 21 колонка для `users` и 26 для `reminders`, суммарно 47.
`Base.metadata.create_all` создаёт таблицы «как сейчас», а списки
досыпают колонки в старые базы. Плюс два data-миграции под
`_run_once`/`schema_migrations`.

Механизм рабочий и намеренный (Alembic отвергнут явно). Но он уже
доехал до границы: типы колонок дублируются между `models.py` и
строковыми литералами в `engine.py` и могут разойтись молча; удалить или
переименовать колонку нельзя вовсе; порядок применения не выражен.

**Предложение (без Alembic).** Не расширять список руками, а
генерировать его из метаданных: пройти по `Base.metadata.tables`,
сравнить с `inspect(conn).get_columns(...)` и досыпать недостающее,
получая тип из самой модели. Тогда `models.py` остаётся единственным
источником истины, а `engine.py` — механизмом. `_run_once` для
data-миграций сохранить как есть. Ограничение (нельзя удалять колонки)
остаётся и должно быть записано в docstring как осознанная граница.

## 4.4. Комментарии ссылаются на удалённые документы

31 ссылка в production-коде на `REWORK_PLAN_3`, `P1-4`, `P1-7`, `P1-12`,
`W1`, `W3`, `W6`, `BUG-C1`, `BUG-D1`, `EDGE-5`, `CRIT-6`, `fix(2.2)`,
`3.5` и т. д. Документы `REWORK_PLAN_3` и `REWORK_PLAN_4` удалены
(коммит `25408fb`), нумерация `P1-*`/`W*` не существует нигде в репозитории.

Для нового человека (и для агента) это ссылки в никуда: сам текст
комментария обычно объясняет суть, но идентификатор создаёт ложное
впечатление, что где-то есть контекст.

**Предложение.** При правке любого файла — заменять идентификатор на
суть («не менять на exact-match: любой простой даунтайм теряет бриф»),
оставляя объяснение. Не делать это отдельным массовым коммитом: диффы по
комментариям затрудняют `git blame` без пользы. Отдельный шаг: в
`BOT_OVERVIEW.md` завести раздел «принятые инварианты» и перенести туда
те объяснения, которые важнее одного файла.

## 4.5. `Reminder` — одна таблица на четыре сущности

Модель несёт 40+ колонок и обслуживает: разовую задачу, повторяющуюся
задачу, привычку с фиксированным временем (`is_habit`) и «текучую»
привычку (`is_fluid_habit`). Отсюда `is_habit_like()` с пятью
эвристиками, отдельные пары счётчиков (`habit_streak_*` /
`fluid_streak_*`), поля, значимые только для одного из типов
(`fluid_planned_time`, `nagging_sent_count`, `last_nag_message_id`), и
необходимость в каждом запросе писать `is_fluid_habit.is_(False)`.

**Предложение — не нормализовать.** Разделение на таблицы означало бы
переписать все DAO, все джобы и все хендлеры ради чистоты схемы,
которая на SQLite не даёт выигрыша. Соразмерный шаг — ввести на уровне
Python явный дискриминатор:

```python
class ReminderKind(StrEnum):
    TASK = "task"; RECURRING = "recurring"; HABIT = "habit"; FLUID_HABIT = "fluid_habit"

@property
def kind(self) -> ReminderKind: ...
```

и постепенно заменять на него `is_habit_like()` и разбросанные
`getattr(r, "is_fluid_habit", False)`. Схема не меняется, читаемость
растёт, миграция — по одному месту за раз.
