## 0. Подготовка и общие инварианты

Рабочая папка — /workspace/porabot. Используй имеющуюся копию и .venv; облачная задача уже изолирована, отдельный worktree создавать только по прямому запросу. Не затирай чужие изменения. Проверь текущий commit и git status; ссылки на строки из аудита могут устареть, ориентируйся на функции.

Текущий стек: Python 3.11, aiogram 3, SQLAlchemy + aiosqlite, APScheduler, простой JS/CSS без сборки. Для изменения интерфейса не нужны смена фреймворка, PostgreSQL или общий рефакторинг приложения.

Базовая проверка из корня:

~~~bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check --no-cache .
PIP_CACHE_DIR=/workspace/.cache/pip .venv/bin/python -m pip check
.venv/bin/python scripts/scan_secrets.py --no-history
~~~

В исходной версии 701 тест проходит; это ориентир, не жёстко заданное ожидаемое число после добавления тестов. Не ослабляй проверки ради зелёного результата. Для каждой подтверждённой ошибки сначала добавь тест, который падает на исходной реализации.

Обязательные инварианты всех этапов:

1. Подтверждение пользователю означает успешно зафиксированное изменение. При ошибке commit нельзя показывать успех. Сохраняй существующее восстановление jobs/данных при сбое планировщика и транзакции; не меняй порядок побочных эффектов механически.
2. Любое изменение проверяет владельца по серверным данным. Старый callback, повторное нажатие, чужой ID, удалённый объект и перезапуск между действиями обработаны явно.
3. В БД сохраняются текущие соглашения об UTC; календарные дни вычисляются в зоне пользователя. Редактирование названия не меняет время, snooze не сдвигает RRULE, завершение не создаёт второе событие того же цикла.
4. Существующие callback_data продолжают распознаваться. Новые callback_data не превышают 64 байта UTF-8; не кодируй в них длинный запрос, название или весь список ID.
5. RU/EN/ES равноправны: новые ключи, параметры форматирования, кнопки, ошибки и помощь добавляются сразу на трёх языках. Не полагайся на случайные русские fallback-строки.
6. Telegram-сообщение укладывается в лимит 4096 символов с безопасным экранированием. Лимиты кнопок и длины текста соблюдаются пагинацией, а не потерей доступа к объектам.
7. Настройки существующих пользователей и история событий сохраняются. Миграции повторяемы и проверяются на старой SQLite-схеме. Новые значения по умолчанию применяются только к новым настройкам/объектам.
8. initData проверяется сервером; фронтенд не определяет владельца данных из непроверенного user_id. Нельзя ослаблять HMAC или возраст входа ради локального прототипа.
9. Не логируй текст задач, аудио, initData, токены и персональные экспортные файлы. Новые продуктовые метрики вводи отдельно с явным набором событий и сроком хранения.

## Этап A. Корректность действий и времени

Закрывает UX-01, UX-02, UX-03, UX-09. Изменения допустимо разделить на четыре небольших PR.

### A1. Разделить отмену создания и закрытие настройки

Файлы: bot/keyboards/inline.py, bot/handlers/commands.py, bot/handlers/reminders_wizard.py, bot/handlers/reminders_listing.py, bot/lexicon/{ru,en,es}.py.

- Убери cancel_wizard из новой клавиатуры сохранённой задачи. Добавь отдельный callback для «Закрыть настройки» / возврата к карточке.
- Раздели состояния: создание без сохранения, редактирование сохранённого объекта и просмотр. Отмена редактирования сбрасывает ввод и показывает неизменённую задачу.
- Для старого cancel_wizard без активного создания используй нейтральное «Действие закрыто. Сохранённые задачи не изменены». Не удаляй задачу и не выдавай сообщение об отменённом создании.
- /cancel в настройке времени/языка тоже не должен сообщать об отмене создания напоминания.
- Проверь извлечение ID в _reminder_id_from_card: новая карточка по-прежнему поддерживает изменение ответом.

Приёмка: «сохранить → изменить → закрыть» оставляет ровно одну задачу и её job; «создать → отменить до сохранения» не оставляет задачи/job; старые сообщения работают после перезапуска.

Тесты: расширить test_saved_task_card.py и добавить регрессии callback_cancel для отсутствующего FSM, активного создания, редактирования и настройки. Проверять состояние БД/job, а не только наличие кнопки.

### A2. Уточнять неоднозначное время привычки

Файлы: bot/handlers/habits.py, bot/handlers/reminders_shared.py, bot/states/reminder.py либо локальный HabitState, bot/keyboards/inline.py.

- Повторно используй решение о date_only/confidence, но не направляй привычку в сервис, который сохраняет обычную задачу. При необходимости выдели небольшую чистую функцию классификации результата парсера.
- Для «в понедельник» спроси час; сохранение и job до ответа запрещены. Сохрани распознанную дату начала. Для низкой уверенности покажи предварительное время и явное подтверждение.
- Перед сохранением покажи/подтверди смысл: «Ежедневно в 09:00, начиная с понедельника». Не трактуй произвольную дату как просьбу создать только недельный повтор.
- Для повторного неверного ввода сохраняй название и выбранную дату. Отмена не создаёт черновой Reminder.
- Раннее время сегодня переходило на следующий ежедневный слот; сохрани это корректное поведение и объясни дату первого срабатывания.

Приёмка: «в понедельник» не создаёт полуночный job; ответ «09:00» создаёт одну ежедневную привычку с нужной датой начала; понятный ввод «каждый день в 09:00» не получает лишние подтверждения при уверенном разборе. Проверить RU/EN/ES и DST.

Тесты: реальные примеры парсера плюс handler-интеграция для date_only, низкой уверенности, отсутствия времени, отмены и сбоя commit. Тест из аудита должен падать до исправления.

### A3. Явно показать область изменения повторения

Файлы: reminders_wizard.py, reminders_snooze.py, reminders_shared.py, reminders_repeat.py, inline.py, словари.

- На повторяющейся задаче различать «Отложить текущее напоминание» и «Изменить расписание». Первый путь использует текущую snooze-логику, второй меняет якорь осознанно.
- Ответ на карточку повторяющейся задачи сначала уточняет область изменения; у одноразовой задачи сохраняется быстрый путь.
- Показывать полное название, локальную дату/время ближайшего напоминания, правило и выбранную область изменения.
- Для ограниченного COUNT/UNTIL определить результат до сохранения. В первом исправлении допускается сохранить текущую семантику с явным предупреждением о перезапуске COUNT; не внедрять сложные исключения серии скрыто. Отдельно отметить, если выбранное время находится за UNTIL.
- «Только текущее» не значит отмена следующего очередного повтора. Если одновременно уже наступает следующий цикл, использовать существующие идентификаторы цикла и сообщать актуальное состояние.

Приёмка: snooze понедельника не меняет вторник; изменение расписания меняет будущие срабатывания после подтверждения; отмена вопроса не меняет ничего; COUNT/UNTIL/DST и старое сообщение проверены.

### A4. Разделить фиксированное смещение и региональный пояс

Файлы: settings/locale_time.py, inline.py, utils/time_ext.py и все места чтения user.timezone, словари, тесты смены пояса.

- Добавь путь выбора IANA-региона и отдельный путь фиксированного смещения. У регионального пояса явно указано автоматическое сезонное время.
- Числовой ввод -3:30 должен сохранять фиксированные -03:30, а не автоматически выбирать America/St_Johns.
- Введи единый resolver поддерживаемого формата хранения фиксированного смещения. Перед выбором формата проверь все pytz.timezone(user.timezone), dateparser, RRULE и ICS: произвольная строка UTC-03:30 сейчас не обязана ими поддерживаться. Миграция и общий resolver нужны, если формат расширяется.
- Предпросмотр содержит местное время «сейчас» и пояс; подтверждение применяет выбор. Популярные города остаются быстрыми кнопками, поиск принимает IANA и поддерживаемые локализованные названия.
- Старые сохранённые зоны остаются прежними. Сохрани существующее предложение перенести фиксированные привычки после смены зоны.
- В первой версии без расширения модели допустимо запретить неоднозначное числовое сопоставление и предложить явный регион, но такой вариант считать временным исправлением UX-09, а не полной поддержкой фиксированных дробных смещений.

Приёмка полной версии: -03:30 одинаков в январе и июле; America/St_Johns меняется по правилам региона; проверены +05:45, +14:00, -12:00 и некорректные значения. Смена пояса не меняет одноразовые UTC-даты молча и не создаёт пачку догоняющих уведомлений.

### B2. Явное подтверждение массовой отметки

Файлы: reminders_listing.py, services/missed_recovery.py, inline.py, FSM/модель контекста из B1, словари.

- Замени «Сделать всё» на «Отметить выполненными…».

Приёмка: новая задача, ставшая просроченной после открытия экрана, не отмечается; double-tap даёт один результат; старый токен не применяет другую выборку; отказ commit оставляет все данные неизменными.

## Этап C. Цельный Mini App

Закрывает UX-06, UX-07, UX-08. Файлы: bot/webapp/{app.js,index.html,style.css}, services/{miniapp,webserver}.py, тесты Mini App.

### C1. Язык и показатели

- Добавь полный словарь ES, проверь одинаковый набор ключей и html lang. Язык профиля имеет приоритет; до его загрузки язык Telegram допустим только как предварительная локализация, не источник авторизации.
- Показывай «Устойчивость: N/100», отдельную краткую справку и фактические выполнения за явно выбранный период. Не меняй compute_habit_score.
- Пустая история: «Пока нет отметок», затем действие к привычкам. Нулевая устойчивость при известной истории — отдельное состояние.
- Текущий heatmap.total — число записанных исходов, а не количество запланированного. Для первого релиза используй честные подписи «Выполнений», «Пропусков», «Нет записей». Для доли от плана нужен отдельный расчёт/поле planned_total с согласованной политикой пауз и незакрытого дня.

### C2. Состояния загрузки и ошибок

- Загружай профиль и данные так, чтобы успешный блок можно было показать при ошибке соседнего. Локализация может обновиться после получения профиля.
- Добавь прикладной таймаут запроса 10 секунд, явные loading/empty/ready/error и доступную кнопку повтора. Повтор не сбрасывает готовый блок и выбранный период.
- Для 401 прекращай автоматические повторы, предложи заново открыть Mini App из бота; для 429 уважай Retry-After; для сети/5xx предложи ручной повтор без сырого HTTP-текста.
- Статус сообщается через role=status/aria-live; ошибка не обозначается только красным. Не выводи initData и содержимое исключения, которое может содержать URL/секреты.
- Закрытие экрана/новый запрос отменяет старый; поздний ответ не перетирает более свежие данные. Не создавай бесконечный polling.

### C3. Доступный календарь прогресса

- Начни с месячного вида и переключения месяца. Выравнивай недели, показывай названия дней, месяц/год и выбранную дату. Локальный день задаёт API профиля/статистики, не часовой пояс браузера.
- Интерактивная цель не меньше 24×24 CSS px без перекрытий; основные кнопки и альтернативный список дней — предпочтительно 44×44. На 320 px обеспечь работоспособный календарь либо переключение в список.
- Используй семантические кнопки. Для календарной сетки — одно управляемое Tab-вхождение и стрелки либо другой доступный шаблон; не оставляй 90 последовательных Tab-остановок.
- При выборе даты сохраняй фокус на управляющем элементе и объявляй подробности через live-region. После закрытия подробностей возвращай фокус туда, где пользователь был.
- Нулевой день и день с пропусками различимы по тексту. Не выдавай событие «нет данных» за «не выполнено».
- Проверить Telegram themeChanged, светлую/тёмную тему, длинные имена, 200% увеличение текста и safe-area на мобильном устройстве. Оценить контраст реальных цветовых пар; сами переменные темы не гарантируют доступность.

Приёмка C: es-профиль показывает испанские тексты; score=20 не превращается в 20% выполнений; 500 heatmap оставляет scores; timeout снимает бесконечную загрузку; 401 предлагает восстановление входа; календарь работает касанием/клавиатурой и в узком окне.

Тесты: существующие API-интеграции + frontend-тесты поведения в DOM/браузере. Если в проекте по-прежнему нет JS-runner, добавь минимальный обоснованный инструмент и lockfile; не вводи React ради тестов. В сценариях UI используй синтетический Telegram SDK и подписанные тестовые initData, не отключение серверной проверки. Реальный Telegram-клиент остаётся отдельной проверкой; её отсутствие явно указать в PR.

## Этап D. Ежедневный опыт и тексты

Закрывает UX-11, UX-12, F1 и F4.

### D1. «Сегодня» и отметка текущего цикла

Файлы: handlers/menu.py, habits.py, reminders_listing.py, inline.py, DAO, сервисы завершения.

- Основное меню оставь компактным. В списке задач «Сегодня» доступно одним нажатием; в привычках сначала показывай активные привычки текущего дня, затем создание.
- Ежедневный обзор различает просроченное, назначенное время, гибкие привычки и паузу. Не дублируй фиксированную привычку одновременно как обычную задачу и привычку.
- «Сделано» доступно у текущего разрешённого цикла. Для фиксированной привычки callback содержит due/cycle идентификатор; для гибкой — локальную дату. Вынеси общее доменное действие из Telegram-обработчика, если оно нужно двум интерфейсам.
- Досрочная отметка не должна потом получить missed от sweeper или повторное напоминание того же цикла. Старая карточка вчерашнего дня не отмечает сегодняшний день.
- Откат отметки использует существующий механизм восстановления, а не отдельный набор правил. Паузу показывай с датой возобновления и доступным действием.
- Запись через Mini App не обязательна в этом этапе: сначала полноценные действия в чатовой панели. Если добавляются write-endpoints, они вызывают тот же доменный сервис, проверяют auth/владельца/цикл и идемпотентность.

Приёмка: привычку можно отметить за одно нажатие из видимой строки; повторный tap не увеличивает счётчики; после рестарта результат виден; просроченный callback и пауза не создают неверное событие.

### D2. Явные настройки уведомлений

- После первой сохранённой задачи ненавязчиво предложи «Только напоминания», «Напоминания и сводки», «Настроить». Не блокируй создание следующей задачи выбором пресета.
- Показать, какие существующие поля изменит пресет, прежде чем применять. «Только напоминания» отключает briefs/habit reports/missed digest, но не задачи. Настройки тихих часов меняются только явно.
- Для новых фиксированных привычек повторные сообщения выключены по умолчанию. В настройках можно включить их и увидеть интервал/максимум. Старые привычки не мигрировать на новый режим без выбора пользователя.
- При включённой тишине покажи: напоминания переносятся согласно текущей политике, сводки приходят без звука; исключения для привычек видны.

Приёмка: выбор пресета атомарен и соответствует предпросмотру; не меняет посторонние настройки; старая учётная запись без выбора сохраняет свой режим; первое включение привычки не создаёт скрытой цепочки повторов.

### D3. Микротексты и помощь

- «Утро» в кнопке времени заменить на точную дату: «Завтра, 09:00»; учитывать выбранную дату и локальную зону.
- Ошибка разбора: «Не понял время. Напиши, например: завтра в 18:30»; предложить выбор времени, сохранив название. Ошибка сервера не должна обвинять формат текста.
- До «Не сегодня» объясни, что это пропуск, а не пауза; серия прервётся, история останется. Пауза — отдельное действие. Не меняй формулу и исторические события под видом нового текста.
- После сброса данных: «Задачи, привычки и настройки удалены. История платежей сохранена для поддержки». Не обещать удаления всех данных.
- /help: короткий обзор создания, редактирования ответом, поиска, тегов, отмены и настроек; длинную справку разбить на темы. Примеры проверить настоящим парсером на RU/EN/ES.
- Сократи повторы приветствия при онбординге; явно покажи местное время. Не выбирай пояс по языку Telegram и не назначай случайный город.

## Этап E. Недельные цели привычек — отдельный релиз F2

Цель: «Тренировка 3 раза в неделю» без привязки к понедельнику/среде/пятнице. Это новая модель периода, не просто ещё один RRULE и не существующий fluid mode.

Сначала напиши короткую схему данных и таблицу переходов; затем миграцию, доменные сервисы, UI и тесты. Предлагаемый модуль services/habit_targets.py. Точки интеграции: models/engine/DAO, habit_sweeper, habit_reports, habit_pause, timezone migration, miniapp, user_data/export/reset/retention, карточки и scheduler.

Зафиксированная семантика v1:

- Цель N от 1 до 7; максимум одно выполнение за локальный календарный день. Количественные цели «8 стаканов» не входят в этот этап.
- Период — понедельник 00:00 до следующего понедельника 00:00, правая граница исключена, в зоне привычки/пользователя, зафиксированной для периода. ID периода и локальная дата обязательны.
- UI: «2 из 3 на этой неделе», отдельно расписание напоминаний. Норма не подразумевает N уведомлений подряд и не генерирует ежедневные missed.
- Неделя считается достигнутой, когда done_days >= target. Пока неделя не закончилась, недобор не является провалом. Закрытие недели идемпотентно.
- Первая неполная неделя — ознакомительная, без штрафа за недобор. Это явно видно в интерфейсе.
- Для v1 любая неделя, затронутая явной паузой, нейтральна для серии/оценки недельных целей; выполненные отметки сохраняются. Показывать «Неделя с паузой, без оценки». Это осознанный простой продуктовый выбор, а не пропорциональный пересчёт нормы. Полноценное пропорционирование — отдельная версия.
- Изменение N/пояса действует со следующего периода. Текущий период и история не пересчитываются молча. Ручная смена пояса не даёт второй отметки за тот же идентифицированный день/цикл.
- Действующие ежедневные привычки сохраняют старую семантику. У недельных отдельная «серия успешных недель»; не выдавать её за серию дней. Устойчивость, если показывается, считается по закрытым оцениваемым неделям и подписана соответственно.
- В ICS у недельной нормы без фиксированных слотов нет вымышленной даты выполнения; экспортировать только явно назначенные напоминания либо документированно исключить такую норму из feed.

Критерии приёмки: 3 отметки в разные дни дают 3/3; повтор в один день остаётся 1; переход воскресенье→понедельник начинает новый период; неделя с паузой нейтральна; рестарт/двойной sweeper не дублирует закрытие; отчёт, экспорт, reset и Mini App одинаково трактуют период. DST, поздний callback, отмена отметки и сбой commit покрыты тестами.

Запрещено: переиспользовать ежедневные missed как «не хватило повторов за неделю», смешивать разные циклы в старой UNIQUE(reminder_id, cycle_key), без миграции превращать имеющуюся привычку в недельную.

## Этап F. Входящие без даты — отдельный релиз F3

Цель: сохранить «проверить страховку» сейчас, не придумывая время напоминания.

Предпочтительный минимальный дизайн — отдельная сущность InboxItem. Не делай Reminder.execution_time nullable без полного анализа всех jobs/DAO/фильтров. Поля: владелец, текст, теги/приоритет по текущей семантике, created_at, состояние, связь с созданным Reminder при преобразовании. Точные имена выбрать в реализации.

- При отсутствии даты сохранить текущий вопрос о времени и добавить явное «Во входящие без напоминания». Не отправлять туда любой нераспознанный текст автоматически.
- Подтверждение: «Сохранено во входящие. Напоминание не назначено». Во входящих видны «Назначить время», «Изменить название», «Удалить».
- Назначение времени использует общий парсер и уточнения из A2. Переход inbox→scheduled атомарен и идемпотентен: один исходный объект даёт максимум один Reminder. При ошибке сохранения/планирования запись остаётся доступна и не показывается успех.
- У входящего нет job, просрочки, nagging, участия в missed recovery или ICS. Не создавай дату-заглушку 2099 года.
- Поиск/пагинация поддерживают входящие отдельно, без смешения с просроченными. Экспорт и сброс данных включают новую сущность.
- Лимит активных входящих v1 — 200 на пользователя; ограничение видно до потери ввода. Оно независимо от существующего лимита Reminder и не обходится двойным запросом.

Приёмка: сохранение без даты не создаёт scheduler job; повторное назначение времени не создаёт дубль; преобразование учитывает лимиты Reminder; отмена назначения оставляет InboxItem; failed commit сохраняет исходный объект; чужие ID недоступны; после рестарта и экспорта данные полны.

## Исследовательские этапы F5/F6

**Личные шаблоны:** сначала проверить, повторяются ли у пользователей одинаковые структуры задач. MVP — сохранить шаблон вручную, назвать, применить с предпросмотром новой даты; ни один относительный срок не копируется как старая абсолютная дата. ## Итоговая проверка и формат сдачи

Перед каждым PR: целевые регрессии; затем полный pytest, ruff и сканер текущего дерева. После изменения Mini App — frontend-проверки и браузерные сценарии, после модели — повторная миграция и интеграции со scheduler/export/reset. Повторять весь набор после новых изменений, а не бесконечно на неизменном коде.

Обязательные ручные сценарии перед релизом:

1. Создать, переименовать, перенести и удалить задачу; отменить удаление; вернуться в тот же фильтр.
2. Создать привычку с датой без часа, уточнить час; отметить до уведомления; отменить отметку; поставить на паузу.
3. Найти запись за первой страницей и открыть полное длинное название.
4. Открыть массовое подтверждение, изменить набор данных другим действием, затем подтвердить — набор не расширяется.
5. Повторяющаяся задача: отдельно snooze и изменение расписания, включая COUNT/UNTIL.
6. Mini App: ES, светлая/тёмная тема, 320 px, крупный текст, клавиатура/экранный диктор, 401/429/500/timeout, частично готовый экран.
7. Смена регионального и фиксированного пояса; сохранение правильного времени после DST и перезапуска.

Сдача каждого этапа: ID закрытых находок → изменившееся поведение → файлы → выполненные тесты и их результат → непройденные/непроверенные сценарии → миграции и обратная совместимость. В отчёте различать локальный mock, настоящий локальный HTTP, браузер и Telegram-клиент.

Финальная приёмка A–D: все UX-01–12 исправлены либо конкретный оставшийся подпункт явно обозначен; E/F не выданы за готовые. Не считать обновление документа или появление кнопки реализацией полного сценария. Для публикации/production-развёртывания нужен отдельный пользовательский запрос.
