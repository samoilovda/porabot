# Porabot — предложения по развитию функционала

Документ отвечает на вопрос «что делать дальше», а не «что починить» —
починка вынесена в `REWORK_PLAN_3.md`. Основан на разборе текущего кода
(9672 строки production-кода, 178 тестов) и на обзоре конкурирующих
продуктов: Telegram-ботов-напоминалок и трекеров привычек.

Каждое предложение оценено по трём осям: **отдача** (что получает
пользователь), **цена** (что придётся написать, с указанием конкретных
файлов) и **риск**. Оценка трудоёмкости — в человеко-днях для разработчика,
знакомого с кодовой базой.

---

## 1. Где продукт находится сейчас

**Сильные стороны, которых нет у конкурентов:**

- **Создание задачи одной фразой на трёх языках.** Skeddy — самый известный
  Telegram-бот-напоминалка — тоже умеет естественный язык, но повторяющиеся
  задачи у него настраиваются в **отдельном веб-интерфейсе** на skeddy.me.
  У Porabot всё внутри чата.
- **Привычки и напоминания в одном продукте.** Обычно это разные приложения:
  Todoist/Skeddy для задач, Streaks/Loop/Habitica для привычек. Здесь оба
  контура работают на общей модели и общем планировщике.
- **Корректность на границах, которой обычно нет.** DST-переходы,
  восстановление после простоя, идемпотентность отметок, атомарные claim-ы
  слотов рассылки, event-log привычек. Это не видно пользователю, но именно
  на этом самодельные боты и ломаются.
- **Три языка целиком**, включая разбор времени, а не только интерфейс.

**Слабые стороны, которые видны пользователю:**

- Повтор ограничен четырьмя пресетами (нет / день / будни / неделя), хотя
  движок под капотом поддерживает полный RRULE.
- Нет ввода времени текстом на шаге выбора времени (см. `REWORK_PLAN_3.md`
  §2.1–2.2) — при том, что это главная фича продукта.
- Плоский список задач без тегов, поиска и приоритетов.
- Стрик привычки бинарный и хрупкий: один пропуск — ноль.
- Нет никакой визуализации прогресса, только текстовые отчёты раз в неделю.
- Нет экспорта данных: «удалить всё» есть, «забрать своё» — нет.

## 2. Что делают конкуренты

### Telegram-боты

| Продукт | Что умеет | Чего не умеет |
|---|---|---|
| **Skeddy** | Естественный язык, заметки, повторы, веб-интерфейс | Голосовые сообщения; извлечение задач из контекста переписки; привычки/стрики |
| RemindMegaBot, SmartScheduler | Базовые напоминания, повторы | NLP-качество, мультиязычность, привычки |

Вывод: ниша «напоминалка в Telegram» занята, но **никто не закрыл голосовой
ввод и никто не совместил его с трекером привычек**. Это и есть два
свободных направления.

### Трекеры привычек

| Продукт | Ключевая механика | Что стоит перенять |
|---|---|---|
| **Loop Habit Tracker** | *Habit score* — процент «силы» привычки, который **плавно снижается** при пропуске и плавно восстанавливается, вместо обнуления стрика | Прямо ложится на существующую таблицу `habit_events` |
| **HabitKit** | Учёт **частичных и множественных** выполнений за день; тепловая карта-сетка | Сетка-визуализация; «выпил 5 из 8 стаканов» |
| **Streaks** | Жёсткий лимит 12 привычек — сознательное ограничение против расфокуса | Мягкое предупреждение при >10 привычках |
| **Habitica** | Геймификация (RPG, уровни, снаряжение) | **Не перенимать** — см. §7 |

Ключевая идея из Loop: бинарный стрик наказывает за один пропуск так же,
как за десять, и люди бросают трекер после первой осечки. Плавная метрика
это лечит — и у Porabot **уже есть данные для неё**: `habit_events` с
`outcome ∈ {done, not_today, missed}` и `local_date`.

### Что появилось в Telegram Bot API за 2026 год

- **Bot API 9.5** (март 2026): `sendMessageDraft` открыт всем ботам —
  стриминг ответов по мере генерации.
- **Bot API 10.1** (июнь 2026): Rich Messages — `sendRichMessage` /
  `sendRichMessageDraft`, структурированный текст и потоковая выдача.
- **Telegram Stars**: `getMyStarBalance` — платежи внутри Telegram без
  внешнего эквайринга.
- **Mini Apps**: с 20 июля 2026 ужесточена изоляция по origin.

Практический вывод: монетизация через Stars технически проста, а Mini App
остаётся штатным способом показать графику (тепловые карты привычек),
которую в чате не нарисовать.

## 3. Уровень 1 — быстрые победы (1–3 дня каждая)

Всё в этом разделе делается **внутри существующей архитектуры**, без новых
внешних зависимостей и без новых сервисов.

### 3.1. Полноценный конструктор повторов ⭐ приоритет №1

**Отдача:** высокая. **Цена:** 2 дня. **Риск:** низкий.

Сейчас `callback_edit_repeat` (`bot/handlers/reminders.py:552-595`)
циклически перебирает четыре варианта по нажатию. При этом
`next_occurrence_utc` (`bot/utils/time_ext.py:1173`) использует
`dateutil.rrulestr` и **поддерживает произвольный RRULE уже сегодня** — вся
машинерия, включая DST-корректный расчёт, готова.

Что добавить (это чистый UI поверх работающего движка):
- «каждые N дней» → `FREQ=DAILY;INTERVAL=N`
- выбор конкретных дней недели чекбоксами → `FREQ=WEEKLY;BYDAY=MO,WE,FR`
- «по выходным» → `FREQ=WEEKLY;BYDAY=SA,SU`
- «раз в месяц, N числа» → `FREQ=MONTHLY;BYMONTHDAY=N`
- «последний рабочий день месяца» → `FREQ=MONTHLY;BYDAY=MO,TU,WE,TH,FR;BYSETPOS=-1`
- ограничение по числу повторов / дате окончания → `COUNT=` / `UNTIL=`

Что затрагивает: `bot/keyboards/inline.py` (новое подменю вместо
одной циклической кнопки), `_rrule_text` (`reminders.py:74-84` — сейчас
распознаёт только 4 шаблона, нужен человекочитаемый рендер произвольного
правила), лексиконы ru/en/es.

Почему первым: соотношение «объём кода / ценность» здесь лучшее во всём
документе, и это закрывает самую заметную дыру в сравнении со Skeddy.

### 3.2. Habit score вместо голого стрика ⭐ приоритет №2

**Отдача:** высокая. **Цена:** 2 дня. **Риск:** низкий.

Механика Loop: вместо «стрик = 0 после первого пропуска» — экспоненциальное
скользящее среднее по выполнениям, которое **падает постепенно**.

Данные уже есть: `habit_events` содержит по строке на каждый разрешённый
цикл с `outcome` и `local_date`, `HabitEventDAO.get_events_in_range` умеет
их доставать. Считать score можно в `bot/services/habit_reports.py`
рядом с существующим `_aggregate`.

Показывать: в списке привычек (`cb_habit_list`, `habits.py:344`) рядом со
стриком, в недельном отчёте, в мотивационном блоке дашборда.

Стрик **не убирать** — он нагляден и уже реализован. Score его дополняет:
«🔥 3 · 💪 78%» читается лучше, чем «🔥 0» после одного пропуска.

### 3.3. Экспорт данных

**Отдача:** средняя. **Цена:** 1 день. **Риск:** низкий.

Сейчас есть «🗑 Удалить всё» (`settings.py:178-208`), но забрать свои данные
нельзя. Отдавать CSV/JSON документом через `bot.send_document`:
напоминания + `habit_events` + настройки.

Побочная польза: делает удаление аккаунта психологически проще (сначала
выгрузи, потом удаляй) и снимает вопросы про переносимость данных.

### 3.4. Поиск и фильтр в списке задач

**Отдача:** средняя. **Цена:** 1–2 дня. **Риск:** низкий.

Пагинация по 25 (`_TASKS_PAGE_SIZE`) появилась потому, что задач бывает
много — но искать среди них нечем. Добавить `/find <текст>` и фильтры
«сегодня / эта неделя / просроченные / повторяющиеся». Запросы ложатся в
`ReminderDAO` рядом с `get_overdue_pending_tasks`.

### 3.5. Тихие часы: выходные и исключения

**Отдача:** средняя. **Цена:** 1 день. **Риск:** низкий.

Сейчас тихие часы — одно окно `start`–`end` на все дни
(`bot/utils/time_ext.py:1158-1170`). Добавить отдельное окно для выходных
(«в субботу и воскресенье не раньше 10:00») и флаг «привычки будить могут,
обычные задачи — нет».

### 3.6. Мягкое предупреждение о перегрузке привычками

**Отдача:** низкая, но дешёвая. **Цена:** 0.5 дня.

Streaks сознательно ограничивает 12 привычками. Не вводить жёсткий лимит,
но при создании 11-й показывать подсказку: «Больше десяти привычек
одновременно почти никто не удерживает». Один `if` в `state_habit_time`.

## 4. Уровень 2 — заметные фичи (1–3 недели каждая)

### 4.1. Голосовой ввод ⭐ главная дифференциация

**Отдача:** очень высокая. **Цена:** 1–2 недели. **Риск:** средний.

Skeddy голосовые **не поддерживает**. Между тем «сказать на ходу» — самый
естественный способ поставить напоминание, и Telegram отдаёт голосовые
сообщения ботам штатно.

Как ложится на код: обработчик `F.voice` получает `file_id` → скачивает ogg
→ STT → полученный текст идёт **в существующий `parser.parse`** без единого
изменения в парсере. Затем — уже работающий путь `_handle_parsed_result`, с
уже работающим экраном подтверждения при низкой уверенности
(`_PARSE_CONFIDENCE_THRESHOLD = 0.7`, `reminders.py:61`).

Развилка по STT:
- **Whisper API** (или аналог): качество высокое, поддержка ru/en/es из
  коробки, но это внешняя платная зависимость и +1–3 с латентности.
- **faster-whisper локально**: без внешних вызовов и оплаты за запрос, но
  `small`-модель требует ~1 ГБ RAM и заметного CPU — нынешний контейнер
  под это не рассчитан.

Рекомендация: начать с API за фиче-флагом (`VOICE_ENABLED`,
`STT_PROVIDER` в `bot/config.py`), с жёстким лимитом длины (≤60 с) и
отдельным rate-limit. Так фичу можно выключить одной переменной, если
экономика не сойдётся.

**Обязательное условие:** сначала реализовать шаг 2.7 из
`REWORK_PLAN_3.md` (сейчас голосовое молча игнорируется), иначе провал
STT будет неотличим от «бот сломался».

### 4.2. Гибридный LLM-парсер ⭐

**Отдача:** высокая. **Цена:** 1 неделя. **Риск:** средний.

Текущий парсер — трёхступенчатый конвейер: эвристики → Natasha NER →
dateparser → регексп-фолбэки (`bot/services/parser.py`). Он работает, но:

- тянет тяжёлую цепочку `natasha → yargy → pymorphy2 → docopt`, которая
  ломает сборку (см. `REWORK_PLAN_3.md` §4.3);
- `_NATASHA_LOCK` (`parser.py:37`) **сериализует все разборы глобально** —
  под нагрузкой это узкое место;
- уверенность регексп-фолбэков — 0.5–0.55, то есть половина сложных фраз
  уходит на ручное подтверждение;
- не умеет то, чего не умеет и Skeddy: вытащить задачу из **контекста**
  пересланного сообщения («Встречаемся в четверг у метро в семь»).

Ключ к дешёвой интеграции уже в коде: порог
`_PARSE_CONFIDENCE_THRESHOLD = 0.7` и готовый экран подтверждения. Значит
LLM нужен **не вместо** локального парсера, а как второй эшелон:

1. Локальный парсер отрабатывает как сейчас.
2. Если `confidence >= 0.7` — ничего не меняется, ни одного внешнего вызова.
3. Если ниже — уходим в LLM с промптом «извлеки время и текст задачи,
   верни JSON», и уже её результат показываем в экране подтверждения.

Так внешние вызовы тратятся только на сложные случаи (по грубой оценке
15–25 % входящих), а деградация при недоступности LLM — обратно к
сегодняшнему поведению.

Долгосрочно это же открывает путь к отказу от Natasha и, вместе с ней, от
проблемной цепочки зависимостей.

### 4.3. Списки, теги и приоритеты

**Отдача:** средняя. **Цена:** 1–2 недели. **Риск:** низкий.

Задачи сейчас плоские. Минимально достаточный вариант — теги через `#`
прямо во фразе («купить молоко #дом»), парсер их вырезает в отдельное поле,
список фильтруется по тегу. Отдельная таблица не нужна: `tags TEXT` с
разделителем плюс индекс закрывают сценарий.

Приоритеты (`!1`–`!3`) добавить туда же, влияют на порядок в списке и на
порядок в утреннем брифе.

### 4.4. Календарный фид (ICS, только чтение)

**Отдача:** средняя. **Цена:** 1 неделя. **Риск:** средний.

Отдавать пользователю персональную ссылку на `.ics`-фид с его
напоминаниями, которую можно подписать в Google/Apple Calendar. Реализуется
поверх `Reminder` + `rrule_string` практически напрямую — RRULE это и есть
формат iCalendar.

Цена — необходимость поднять HTTP-сервер рядом с ботом (сейчас его нет
вообще, бот работает на long polling). Токен фида должен быть секретным и
отзываемым.

Это же требование появится для Mini App (§4.6) — имеет смысл делать их
одним заходом.

### 4.5. Делегирование напоминаний

**Отдача:** средняя. **Цена:** 1–2 недели. **Риск:** средний.

«Напомнить жене купить хлеб в 19:00». Технически: deep link
`t.me/bot?start=share_<token>`, получатель подтверждает — создаётся
напоминание у него, автор видит статус.

Осторожно: это первая фича, превращающая персонального бота в
многопользовательского, со всеми вытекающими (согласие получателя, спам,
блокировки). Делать только после того, как §3 и §4.1 закрыты, и
обязательно с явным подтверждением получателя.

### 4.6. Mini App: визуализация прогресса

**Отдача:** средняя-высокая. **Цена:** 2–3 недели. **Риск:** средний.

В чате нельзя нарисовать тепловую карту-сетку — а это главный визуальный
крючок трекеров привычек (HabitKit, Loop). Mini App решает это:
календарная сетка выполнений, графики habit score, массовое редактирование.

Цена: статический фронтенд + хостинг + валидация `initData` + HTTP-слой,
которого сейчас нет. Учитывать ужесточение изоляции по origin с июля 2026.

Делать **после** §4.4 — HTTP-инфраструктура общая.

## 5. Уровень 3 — стратегические ставки

### 5.1. Монетизация через Telegram Stars

**Цена:** 1 неделя. **Риск:** низкий технически, высокий продуктово.

Stars снимают вопрос эквайринга целиком (`getMyStarBalance` и платёжные
методы Bot API). Разумная линия отсечения бесплатного тарифа:
неограниченные напоминания и до 5 привычек бесплатно; голосовой ввод,
LLM-парсер, Mini App и экспорт — в платном.

Важно: **платить придётся именно за то, что стоит денег** — голосовой ввод
и LLM-парсер имеют переменную себестоимость на запрос. Остальное — рычаг
ценности, а не издержек.

### 5.2. Переезд на PostgreSQL и снятие ограничений минутных джобов

**Цена:** 1–2 недели. **Риск:** средний.

Сейчас пять минутных cron-джобов (`daily_briefs`, `missed_recovery`,
`habit_sweeper`, `habit_reports`, `delete_cleanup`) проходят по **всем**
пользователям и пишут в один файл SQLite. Открытый пункт W4 из `AUDIT.md`,
признанный сознательным компромиссом.

Порядок действий, когда упрётесь:
1. Сначала — объединить пять проходов в один (одна выборка пользователей,
   пять обработчиков) и добавить индекс под «кому сейчас пора». Это дешевле
   переезда и снимает бо́льшую часть нагрузки.
2. Только потом — PostgreSQL. Код на это уже рассчитан: `create_engine`
   ветвится по диалекту, `DATABASE_URL` поддерживает `postgresql+asyncpg`,
   а `created_at` намеренно вычисляется на стороне Python именно ради
   переносимости (`models.py:97-99`).
3. Долгоживущие `naive`-datetime при переезде проверить отдельно — на
   PostgreSQL `server_default=func.now()` даёт локальное время сервера,
   а не UTC (это прямо отмечено в комментарии `models.py:208-212`).

### 5.3. Webhook вместо long polling

**Цена:** 3–5 дней. **Риск:** низкий.

Не делать, пока не появится HTTP-сервер по другой причине (§4.4/§4.6).
Тогда — почти бесплатно, и заодно снимает вопрос «polling жив, но висит»
из `REWORK_PLAN_3.md` §4.4.

## 6. Чего делать не стоит

- **Геймификация в стиле Habitica** (уровни, снаряжение, монстры). Porabot
  по тону — спокойный ассистент; RPG-слой потребует много кода и отпугнёт
  ядро аудитории, которая пришла за «написал фразу — получил напоминание».
- **Полноценный проектный менеджер** (проекты, подзадачи, диаграммы,
  командная работа). Это конкуренция с Todoist и Notion на их поле,
  в чужом форм-факторе. Теги и приоритеты (§4.3) закрывают 80 % потребности
  за 10 % усилий.
- **Собственный веб-интерфейс для настройки повторов** — путь Skeddy.
  Именно от него Porabot и отличается в лучшую сторону; §3.1 решает ту же
  задачу, не выводя пользователя из чата.
- **Расширение списка языков раньше §3 и §4.1.** Каждый новый язык — это не
  только лексикон (234 ключа × 3 файла), но и правила разбора времени, и
  тестовое покрытие. Углублять три существующих ценнее, чем добавлять
  четвёртый.
