## 0. Как работать с этим документом

1. Фазы выполняются по порядку: Фаза 1 → 2 → 3 → 4. Внутри фазы порядок
   шагов тоже значим (шаг 1.2 опирается на решение из 1.1).
2. Один шаг = один атомарный коммит (`fix: …`, `feat: …`, `refactor: …`,
   `docs: …`). Не собирай несколько шагов в один коммит.
3. После каждого шага: `python -m pytest -q` — зелёно. Ни одного
   упавшего/пропущенного теста.
4. Для каждого бага Фаз 1–2 — регрессионный тест в `bot/services/test_*.py`
   (или `bot/keyboards/test_*.py`), который **падает до фикса и проходит
   после**. Проверь это явно: закоммить тест, убедись что красный, потом фикс.
5. Новые строки интерфейса добавляются **сразу в ru/en/es** —
   `test_l10n_key_coverage.py` это проверяет и упадёт иначе.

### Инварианты — не трогать

Эти решения приняты сознательно и обоснованы в коде комментариями. Если
кажется, что их надо изменить, — сначала прочитай комментарий рядом.

- **Naive UTC в БД.** `execution_time`, `completed_at`, `habit_active_due_at`,
  `pending_delete_at`, `due_at` — всегда naive UTC. Конвертация в локальное
  время только при рендере.
- **Anti-drift снуза привычек.** Для habit-like recurring `execution_time`
  при снузе НЕ перезаписывается (`bot/handlers/reminders.py:1526-1533`) —
  он якорит rrule.
- **`completed_for_execution_time`** — механизм скрытия выполненного цикла
  повторяющейся задачи. Не заменять на `status`.
- **`cycle_key` + `UNIQUE(reminder_id, cycle_key)`** — идемпотентность
  `habit_events`. `HabitEventDAO.record()` использует `SAVEPOINT`
  (`begin_nested`), а не `session.rollback()` — рестарт всего Unit of Work
  тихо потерял бы изменения вызывающего.
- **Расчёт следующего вхождения rrule в локальной TZ** (`next_occurrence_utc`) —
  иначе ежедневное напоминание уезжает на час при переходе на летнее время.
- **Атомарный claim слота** (`_claim_brief_slot` / `_release_brief_claim`) —
  «занял слот» и «доставил» это разные события.

# Фаза 1 — Критические (порча данных / молчаливая потеря функций)

## Шаг 1.1. Бэкфилл `is_habit=1` выполняется при каждом старте

**Файл:** `bot/database/engine.py:364-382`

**Проблема.** Внутри `init_db` есть одноразовая по смыслу миграция:

```sql
UPDATE reminders SET is_habit = 1
WHERE COALESCE(is_habit,0)=0
  AND COALESCE(is_recurring,0)=1
  AND COALESCE(is_nagging,0)=1
  AND UPPER(COALESCE(rrule_string,'')) LIKE 'FREQ=DAILY%'
```

Никакого guard-а «выполнено однажды» нет — она отрабатывает **на каждом
запуске процесса**. Комментарий говорит «Backfill legacy habits created
before `is_habit` existed», но условие описывает не «legacy-привычки», а
любую задачу с ежедневным повтором и включённым дожиманием.

**Как воспроизвести.** Пользователь создаёт обычную задачу «полить цветы»,
через клавиатуру редактирования включает «🔁 Каждый день» и «🔥 Дожимание».
Это полностью легальный сценарий — обе кнопки для того и существуют. При
следующем рестарте бота (деплой, `docker compose up -d --build`) задача
навсегда становится привычкой.

**Последствия — необратимые для пользователя:**
- задача появляется в «Мои привычки»;
- в уведомлении появляется кнопка «Не сегодня» (`is_habit_like` → True);
- `habit_sweeper` начинает писать ей `missed`-события каждые сутки;
- `apply_habit_streak_completion` начинает считать стрик, и «выполнил позже
  чем через 24 часа» обнуляет его — для обычной задачи это бессмыслица;
- удалить её из списка привычек можно только жёстко, без undo (см. A9).

**Что сделать.**
1. Завести таблицу версий схемы, например `schema_migrations(name TEXT PRIMARY KEY,
   applied_at DATETIME)`, и выполнять этот `UPDATE` только если строки
   `backfill_is_habit_v1` там нет; после успеха — вставлять её.
2. Тот же guard применить к бэкфиллу `last_fired_at`
   (`bot/database/engine.py:384-406`) — он тоже идемпотентен по условию
   `last_fired_at IS NULL`, но его повторный прогон на каждом старте это
   лишняя работа и лишний риск.
3. Не удаляй сам `UPDATE` — на реально старых базах он нужен ровно один раз.

**Регрессионный тест.** `bot/services/test_is_habit_backfill_runs_once.py`:
создать in-memory БД, вызвать `init_db` → создать reminder с
`is_recurring=1, is_nagging=1, rrule='FREQ=DAILY', is_habit=0` → вызвать
`init_db` повторно → убедиться, что `is_habit` остался `0`.

## Шаг 1.2. Обычная задача видна в «Мои привычки» ещё до рестарта

**Файл:** `bot/handlers/habits.py:48-61` (`_is_habit_entry`)

**Проблема.** UI-фильтр списка привычек содержит ту же эвристику, что и
миграция из шага 1.1:

```python
or (
    bool(getattr(reminder, "is_recurring", False))
    and bool(getattr(reminder, "is_nagging", False))
    and str(getattr(reminder, "rrule_string", "") or "").upper().startswith("FREQ=DAILY")
)
```

То есть проблема A1 проявляется в интерфейсе **немедленно**, без всякого
рестарта: обычная ежедневная задача с дожиманием попадает в «Мои привычки»
с кнопкой удаления.

**Что сделать.** После шага 1.1 источник истины — колонка `is_habit`.
Убрать эвристический `or`-блок из `_is_habit_entry`, оставив
`is_habit or is_fluid_habit` плюс исторические признаки
(`habit_active_due_at is not None`, `habit_last_completed_due_at is not None`,
`habit_streak_* > 0`) — они честно указывают на строку, которая уже жила
как привычка.

**Регрессионный тест.** `_is_habit_entry` на объекте
`is_habit=False, is_recurring=True, is_nagging=True, rrule='FREQ=DAILY',
habit_streak_current=0` → `False`.

## Шаг 1.3. Вечерний бриф не приходит тому, кто всё выполнил

**Файл:** `bot/services/daily_briefs.py:199-208`

**Проблема.** Список пользователей для обработки формируется так:

```python
select(User.id).distinct().join(Reminder).where(
    Reminder.status == "pending",
    User.briefs_enabled.is_(True),
)
```

Одноразовая задача после «Готово» получает `status='completed'`. Значит
пользователь, у которого сегодня была одна задача и он её выполнил,
**выпадает из выборки** и не получает «🌙 Итоги дня» — ровно в том случае,
когда итоги приятнее всего читать. При этом `_build_evening_text` умеет
показывать секцию «✅ Выполнено» и специально её строит.

Вторичное следствие: `last_evening_brief_date` у такого пользователя не
двигается, и логика «утреннее окно уже прошло» (`daily_briefs.py:266-276`)
работает на устаревших данных.

**Что сделать.** Расширить условие выборки: пользователь берётся в обработку,
если у него есть **любая** из:
- pending-задача (`Reminder.status == 'pending'`, `pending_delete_at IS NULL`);
- задача, выполненная сегодня (`completed_at` в границах его локального дня);
- активная fluid-привычка.

Проще и надёжнее: выбрать всех пользователей с `briefs_enabled=True`,
у которых есть хотя бы одна строка в `reminders`, а отсев «нечего слать»
оставить на месте — он уже есть ниже (`if text_sections:` для утра,
`if completed or pending:` для вечера). Сегодняшняя выборка — это
преждевременная оптимизация, которая режет корректность.

Заодно добавь `Reminder.pending_delete_at.is_(None)` — сейчас пользователь
с единственной задачей в окне undo всё ещё попадает в выборку.

**Регрессионный тест.** Пользователь с одной задачей, выполненной сегодня,
на момент `evening_brief_time` получает вечерний бриф с секцией
«Выполнено: 1».

## Шаг 1.4. Брифы не ограничены по размеру и молча теряются

**Файлы:** `bot/services/daily_briefs.py:37-57`,
`bot/keyboards/inline.py:425-446` (`get_evening_wrapup_keyboard`),
`bot/keyboards/inline.py:585-598` (`get_fluid_completion_keyboard`)

**Проблема.** `_build_morning_text` и `_build_evening_text` склеивают строку
на каждую задачу без ограничения количества. `get_evening_wrapup_keyboard`
добавляет **по три кнопки на задачу** без ограничения. Ограничения Telegram:
4096 символов на сообщение, ~100 кнопок на inline-клавиатуру.

Список «Мои задачи» эту проблему уже решил пагинацией (P1-12,
`_TASKS_PAGE_SIZE = 25`) — брифы остались без защиты.

**Почему это потеря, а не косметика.** При превышении лимита Telegram
возвращает `TelegramBadRequest`. `_send_safe` (`daily_briefs.py:121-132`)
ловит его, пробует переслать без Markdown — та же длина, та же ошибка — и
возвращает `True`, что по контракту функции означает «исход финальный».
Вызывающий код видит `delivered = True`, **не освобождает claim**
(`_release_brief_claim` не вызывается) и помечает день как обработанный.
Бриф не приходит вообще и не повторится до завтра, в логах — одна строка
`Bad request sending brief`.

**Что сделать.**
1. Ввести константу `_BRIEF_ITEMS_LIMIT` (предлагаю 20) в `daily_briefs.py`.
2. `_build_morning_text` / `_build_evening_text`: показывать первые N,
   в конце — строка «…и ещё M» (новые ключи лексикона в ru/en/es).
3. `get_evening_wrapup_keyboard` и `get_fluid_completion_keyboard`: принимать
   те же первые N задач (обрезку делать в `daily_briefs`, а не в клавиатуре,
   чтобы текст и кнопки совпадали).
4. В `_send_safe` различать «слишком длинное сообщение» и прочие
   `TelegramBadRequest`: для первого возвращать `False` (retryable), чтобы
   claim освобождался и следующий тик попробовал снова. Проще — проверять
   `len(text) > 4000` перед отправкой и логировать `ERROR` явно.

**Регрессионный тест.** 60 pending-задач → в тексте не больше 20 строк
задач + строка «и ещё 40»; в клавиатуре не больше 20 рядов.

## Шаг 1.5. Недельный отчёт по привычкам теряется на неделю

**Файл:** `bot/services/habit_reports.py:229`

**Проблема.**

```python
if now_local.strftime("%H:%M") != getattr(user, "habit_report_time", "23:50"):
    continue
```

Точное совпадение минуты. Если минутный тик не отработал ровно в эту минуту
— деплой, рестарт, залипший тик, долгий предыдущий проход по большому числу
пользователей — недельный отчёт пропускается **до следующей недели**, а
месячный — до следующего месяца.

Этот же класс проблемы для брифов уже починен окном «время прошло И сегодня
не отправляли» (`daily_briefs.py:256-264`), для recovery-дайджеста тоже
(`missed_recovery.py:522` использует `<`, то есть окно). Отчёты — последнее
место с `!=`.

Комментарий на `habit_reports.py:256-261` эту дыру фактически признаёт:
«this can only actually be retried if the job happens to fire again for the
same minute».

**Что сделать.** Заменить точное совпадение на окно, симметрично брифам:

```python
if now_local.strftime("%H:%M") < report_time: continue
if now_local.weekday() != report_weekday: continue
if user.last_habit_report_date == today_key: continue   # уже есть
```

Атомарный claim (`update … where last_habit_report_date != today_key`) уже
на месте и остаётся единственной защитой от дубля — этого достаточно.

Отдельно проверь: при сдвиге отправки на более позднее время в тот же день
детектор «последнее вхождение этого дня недели в месяце»
(`habit_reports.py:167`) остаётся корректным — он оперирует датой, не временем.

**Регрессионный тест.** Пользователь с `habit_report_time='23:50'`,
`habit_report_weekday` = сегодня, `last_habit_report_date=None`, текущее
локальное время `23:55` → отчёт отправляется.

# Фаза 2 — Высокие (сломанный или лживый UX)

## Шаг 2.1. Тупик в состоянии `choosing_time`

**Файл:** `bot/handlers/reminders.py`

**Проблема.** Для `ReminderWizard.choosing_time` **не зарегистрирован ни один
message-обработчик**. Проверяется тривиально:

```bash
grep -n "@router.message" bot/handlers/*.py
```

Есть `entering_text`, `confirming_parse`, `waiting_for_nag_limit`,
`waiting_for_done_note` — `choosing_time` отсутствует.

Пользователь, которому бот показал клавиатуру выбора времени и который
вместо нажатия кнопки написал «в 18:30», не получает **ничего**. Ни ошибки,
ни подсказки. Выйти можно только `/cancel` или кнопкой главного меню.
Для бота, чья главная фича — «просто напиши фразу», это худший из возможных
провалов.

**Что сделать.** Добавить
`@router.message(ReminderWizard.choosing_time, F.text)`:
прогнать текст через `parser.parse`; если время распозналось — записать в
`state` и уйти в `_save_and_show_edit`; если нет — ответить подсказкой
формата и оставить клавиатуру. Обработчик обязан стоять **после**
`menu_router` (он и так стоит — `reminders_router` последний), и не
перехватывать тексты кнопок меню (проверка `message.text in _MENU_TEXTS`,
как в `handle_task_text:407`).

**Регрессионный тест.** FSM в `choosing_time` + текст «в 18:30» → создан
reminder на 18:30; текст «абырвалг» → ответ с подсказкой, состояние не
потеряно.

## Шаг 2.2. Кнопка «⌨️ Ввести вручную» ничего не вводит

**Файлы:** `bot/keyboards/inline.py:100`, `bot/handlers/reminders.py:466-470`

**Проблема.** Клавиатура выбора времени предлагает кнопку `time_manual`.
Обработчик:

```python
elif "manual" in data_str:
    await state.clear()
    await callback.answer()
    await callback.message.edit_text(l10n["try_again_manual"])
    return
```

FSM очищается, пользователю предлагают «попробовать ещё раз». То есть
функции ручного ввода времени в боте нет — есть кнопка, которая отменяет
операцию. С учётом шага 2.1 это была единственная дверь к вводу времени
текстом, и она заперта.

**Что сделать.** После шага 2.1 обработчик становится тривиальным: не
очищать состояние, оставить `ReminderWizard.choosing_time`, заменить текст
на приглашение «напишите время, например `18:30` или `завтра в 9`».
Введённый текст подхватит обработчик из 2.1.

**Регрессионный тест.** Нажатие `time_manual` → состояние осталось
`choosing_time`, `edit_reminder_id`/`text` в `state` не потеряны.

## Шаг 2.3. Вечерний бриф считает пропущенным то, что ещё не наступило

**Файлы:** `bot/services/daily_briefs.py:354-355`,

## Шаг 3.3. `_next_quiet_end_utc` не нормализует DST

**Файл:** `bot/services/scheduler.py:303-313`

```python

    candidate += timedelta(days=1)

```

`replace()` на pytz-локализованном datetime сохраняет старый объект

`tz.normalize()` / `tz.localize()` (`parser.py:169`, `time_ext.py:1200`).

**Что сделать.** Считать через naive-локальное время и `tz.localize()`,
как в `next_occurrence_utc`. Тест — по образцу
`test_dst_recurring_reminder.py`.

## Шаг 3.4. Undo выполнения может удалить событие не того цикла

При Undo цикл определяется иначе:

**Что сделать.** Прокинуть `cycle_due_ts` в `done_undo_` callback_data
(`get_done_followup_keyboard`, `inline.py:380-400`) и использовать его в
`callback_done_undo` с тем же приоритетом, что в `callback_task_done`.
Обратная совместимость: старый формат `done_undo_<id>` без метки должен
продолжать работать (сообщения с такими кнопками уже в чатах).
