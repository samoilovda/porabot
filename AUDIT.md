## Критические точки

### C1. Напоминания, выпавшие на время простоя бота, теряются навсегда — P0 [проверено] [исправлено]

APScheduler по умолчанию использует `misfire_grace_time = 1` секунда:

```
$ python -c "from apscheduler.schedulers.asyncio import AsyncIOScheduler; print(AsyncIOScheduler()._job_defaults)"
{'misfire_grace_time': 1, 'coalesce': True, 'max_instances': 1}
```

В `bot/__main__.py` `job_defaults` не переопределяется, а на старте нет никакой
регидратации: единственный источник заданий — `SQLAlchemyJobStore`.

```
$ grep -n "schedule_reminder\|add_job\|get_jobs" bot/__main__.py
(пусто)
```

Последствия. Бот лежал 5 минут (деплой, рестарт, падение) → все задания, чей
`run_date` прошёл за это время, APScheduler отбрасывает при `start()` с записью
«was missed by». Триггер `date` одноразовый, задание исчезает из jobstore.

Для обычной задачи это потерянное напоминание. Для привычки — **смерть
привычки**: `execution_time` двигается вперёд только внутри
`SchedulerService._execute_reminder` (`bot/services/scheduler.py:251-267`).
Задание не отработало → `execution_time` навсегда остался в прошлом → нового
задания никто не создаст. Привычка молча перестаёт напоминать; в списке при этом
продолжает висеть как активная.

`missed_recovery` не спасает: он показывает дайджест в 10:00, максимум 5 задач,
раз в сутки, и ничего не перепланирует.

Что делать:
1. `job_defaults={"misfire_grace_time": 3600, "coalesce": True}` в
   `AsyncIOScheduler(...)` — чтобы короткий простой не убивал задание.
2. Регидратация на старте: пройти по `status == "pending"` и
   `execution_time <= now`, поднять пропущенные (или сдвинуть по rrule вперёд).
3. Периодический watchdog: pending-напоминание без соответствующего задания в
   планировщике — аномалия, её надо чинить, а не ждать.

Исправлено (пп. 1–2): `job_defaults` увеличен до часа в `bot/__main__.py`.
Добавлен `ReminderDAO.get_pending_due()` и
`SchedulerService.rehydrate_missed_reminders()` — на старте, после
`scheduler.start()`, поднимает все `pending`-напоминания с `execution_time <=
now`, у которых нет job в планировщике, и перепланирует их на «сейчас».
Пункт 3 (watchdog в рантайме) не сделан — регидратация закрывает только окно
простоя на старте, не отслеживает потери job'ов во время работы.

### C2. `habit_events` переживают удалённую привычку — P0 [проверено] [исправлено]

`habit_events` ссылается на `reminders.id` и `users.id`. Каскадов в схеме нет,
все четыре пути удаления — жёсткий `DELETE`. `HABIT_STATS_PLAN.md` предписывал
чистку только в `cb_del_habit`, но привычка удаляется ещё тремя способами:

- `del_task_` — fixed-привычки попадают в «Мои задачи» (`get_user_reminders`
  отсекает только fluid), а там у каждой строки есть кнопка удаления;
- `edit_delete_` — из списка привычек по кнопке ⚙️ → `task_settings_` →
  `get_edit_keyboard` → «Удалить»;
- `settings_clear_all_confirm` — полный сброс аккаунта.

Воспроизведение до фикса:

```
after delete_by_id -> reminders=0, ORPHANED habit_events=1
```

Коварство в том, что на SQLite это тихо: `PRAGMA foreign_keys` по умолчанию `0`,
FK не проверяются. На PostgreSQL тот же код упал бы с `IntegrityError` — то есть
баг проявится ровно при переезде на прод-СУБД, которую `DATABASE_URL` уже
поддерживает.

Исправлено: `HabitEventDAO.delete_for_user`, вызовы `delete_for_reminder` во всех
путях удаления. Покрыто `bot/services/test_habit_event_cleanup.py` (тесты
проверены на заведомо сломанном коде — падают все четыре).

### C3. Неэкранированный текст пользователя в Markdown — P0 [проверено] [исправлено]

уходит с разметкой Markdown. При этом текст задач и привычек подставляется в
сообщения без экранирования как минимум здесь:

| Место | Строка |

| `habits.cb_habit_list` | `habit_list_item.format(habit=h.reminder_text)` |
| `habits.state_habit_time` | `habit_created.format(habit=habit_text)` |
| `daily_briefs` fluid-подсказки | `fluid_pick_time_prompt.format(habit=...)` |
| `reminders.callback_task_settings` | `task_settings_title.format(text=...)` |

Задача с именем `Купить хлеб_и_молоко` или `Отчёт *срочно*` ломает разметку →

просто не приходит**. Пользователь не видит ни ошибки, ни брифа.

это отдельная задача.

Что делать: провести аудит всех мест подстановки `reminder_text` в сообщения с
разметкой и обернуть в `escape_markdown_legacy`. Плюс тест-инвариант:
«имя задачи со спецсимволами не ломает бриф».

Исправлено: все перечисленные в таблице точки обёрнуты в
`escape_markdown_legacy` (`daily_briefs.py`, `habits.py`, `reminders.py`), а
заодно — не упомянутые в таблице, но той же природы: `ask_time` /
`parse_confirmation_prompt` (текст задачи сразу после ввода, самый частый
путь), `preview`, список задач (`btn_my_tasks` / `refresh_tasks`), история
выполненных (`show_completed`). Тест-инвариант не добавлен — это отдельная
задача, как и написано выше.

### C4. `rollback()` в `record()` уничтожал Unit of Work — P1 [проверено] [исправлено]

`HabitEventDAO.record` ловил `IntegrityError` от гонки на `UniqueConstraint` и
делал `await self.session.rollback()`. Rollback откатывает **всю** транзакцию, а
не только неудавшийся INSERT, — вместе с изменениями, которые вызывающий хендлер
уже внёс в тот же Unit of Work:

```
habit_streak_current: 0 (handler intended 7)
reminder_text       : Workout (handler intended RENAMED)
```

То есть в `callback_task_done` проигранная гонка отменяла бы уже начисленный
стрик. Ветка редкая (нужны два одновременных тапа по одному циклу), но цена
срабатывания непропорциональна.

Исправлено: `async with self.session.begin_nested()` — SAVEPOINT откатывает
только вставку. Заодно `record()` переиспользует `has_event_for_cycle` вместо
дублирующего SELECT; это дало шов, на котором ветка `IntegrityError` тестируется
честно (`test_lost_race_keeps_callers_unit_of_work_intact`).

> Замечание о методике: первые две попытки воспроизвести гонку уходили в раннюю
> ветку `SELECT`, которая тоже возвращает `False`. Оба исхода выглядят одинаково
> снаружи — легко принять непройденную ветку за пройденную. Ветка признана
> проверенной только после того, как `has_event_for_cycle` был замокан.

### C5. `bot/utils/timezone.py` — мёртвый и неправильный код — P1 [проверено] [исправлено]

Модуль на 321 строку с подробными докстрингами, примерами и «API». Его не
импортирует никто:

```
$ grep -rn "utils.timezone\|ensure_timezone_aware\|utc_to_local\|format_for_display" bot --include="*.py" | grep -v "^bot/utils/timezone.py"
(пусто)
```

И это к лучшему, потому что он неверен:

```
utc_to_local(16:00 UTC, Europe/Moscow) = 2026-05-10 16:00:00+00:00   <- ожидалось 19:00+03:00
ensure_timezone_aware(naive, Europe/Moscow) = 2026-05-10 19:00:00+02:30  <- ожидалось +03:00
```

- `utc_to_local` не конвертирует вообще: внутри зовёт `ensure_timezone_aware`,

- `ensure_timezone_aware` использует `dt.replace(tzinfo=pytz.timezone(...))` —
  классическая ловушка pytz, дающая исторический LMT-офсет `+02:30` вместо
  `+03:00`.

Опасность именно в убедительности: докстринги выглядят авторитетно, и следующий
разработчик, которому понадобится конвертация таймзон, с большой вероятностью
возьмёт этот модуль вместо рабочего `bot/utils/time_ext.py`.

Что делать: удалить файл. Рабочая реализация — `time_ext.py`, она покрыта
тестами (`test_time_ext.py`, `test_utc_normalization.py`).

Исправлено: файл удалён.

### W4. Четыре минутных cron-джоба сканируют всех юзеров — P2 [по коду] [сознательно не тронуто]

`daily_briefs`, `missed_recovery`, `habit_sweeper`, `habit_reports` — каждый раз

На текущем масштабе безразлично, но растёт линейно и упрётся раньше, чем всё
остальное.

Что делать (когда упрётся): считать ближайшее время срабатывания на юзера и
планировать точечные задания вместо поллинга; либо фильтровать кандидатов
по времени прямо в SQL.

Не тронуто сознательно: сам аудит указывает, что это вопрос масштаба
("безразлично, растёт линейно"), а не текущая поломка. Исправление —
структурное (планирование точечных заданий вместо polling'а всех 4 джобов) —
не одна строка, а отдельная задача с собственным риском регрессии; в рамках
этой сессии не делал.

### W6. Наивные `created_at`: UTC в SQLite, локальное время в Postgres — P2 [по коду] [исправлено]

`created_at` объявлен как `DateTime` (naive) с `server_default=func.now()`. В
SQLite `func.now()` → `CURRENT_TIMESTAMP` → UTC. В PostgreSQL `now()` → время в
таймзоне сервера. Значение колонки меняет смысл при смене СУБД.

Код это уже предполагает: `habit_sweeper._sweep_fluid_habits` делает
`created_at.replace(tzinfo=timezone.utc)`. На SQLite верно, на Postgres с
не-UTC таймзоной сервера — сдвиг, из-за которого свипер может закрыть или не
закрыть вчерашний день.

Что делать: `DateTime(timezone=True)` + `server_default=func.now()`, либо явно
проставлять UTC на стороне приложения.

Исправлено вторым способом (без миграции схемы): `default=` для `created_at`
у `User` и `Reminder` заменён на Python-колбэк `_utcnow_naive()`
(`datetime.now(timezone.utc)`, naive). SQLAlchemy применяет Python-side
`default` при ORM-инсертах вне зависимости от диалекта, так что значение
всегда UTC — и на SQLite, и на Postgres. `server_default=func.now()` оставлен
как есть — это фолбэк только для сырых SQL-инсертов мимо ORM, и на них
`habit_sweeper` не полагается.

### W8. Ручной ввод таймзоны: только целые часы, без DST — P2 [по коду] [исправлено частично]

`_resolve_timezone_candidate` принимает только `^[+-]?\d{1,2}$` и отображает в
`Etc/GMT±N`. Отсюда два следствия:

- получасовые зоны недоступны — Индия (+5:30), Иран, часть Австралии;
- `Etc/GMT±N` — зоны с фиксированным офсетом без перехода на летнее время.
  Пользователь из Берлина, введший `+2`, получит `Etc/GMT-2` и уедет на час
  зимой.

Пресеты в `get_timezone_keyboard` — настоящие IANA-зоны и этим не страдают;
проблема только у ручного ввода.

Исправлено частично: ручной ввод теперь принимает получасовые/45-минутные
офсеты (`+5:30`, `-3:30`, `+5.5`, ...) и резолвит их в реальные IANA-зоны из
`_HALF_HOUR_TZ_MAP` (Индия, Иран, Афганистан, Непал, Мьянма, Австралия и т.д.)
— значит, для них DST учитывается правильно. Офсеты без известной
IANA-зоны по-прежнему отклоняются с ошибкой (честно, а не тихо неверно).
Целочасовые офсеты по-прежнему резолвятся в фиксированный `Etc/GMT±N` без
DST — это фундаментальное ограничение формата "просто число", а не то, что
можно починить без замены UX на выбор города; в промпте это явно
проговорено.

### N7. `WhitelistMiddleware` написан целиком и закомментирован — P2 [проверено] [частично исправлено]

пояснением «whitelist intentionally disabled (open access)».

- `config.ALLOWED_USERS` не влияет ни на что;
- `validate_config()` печатает «No admin or allowed users configured!» —
  предупреждение о контроле доступа, которого всё равно нет;

решение, не моё): `validate_config` теперь пишет через `logging.warning`, а
не `print`; предупреждение про ADMIN_ID/ALLOWED_USERS заменено на честное —
теперь оно говорит прямо, что контроль доступа отключён мидлварью, а не
делает вид, что зависит от заполненности переменных. Docstring
`DatabaseMiddleware` больше не требует регистрации после несуществующего
`WhitelistMiddleware`. `logging.basicConfig()` в `__main__.py` перенесён
выше `validate_config()`, чтобы это предупреждение тоже шло через
форматированный логгер.
