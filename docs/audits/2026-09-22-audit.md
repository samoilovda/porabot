### A-02 · P1 · Повтор с `COUNT=N` бесконечен

**Где:**
- `bot/utils/time_ext.py:163-167` — `next_occurrence_utc` берёт `dtstart` из **текущего** `execution_time`;
- `bot/services/scheduler.py:716-721` — вызывающий код;
- `bot/handlers/reminders_repeat.py:388-390` — добавление `COUNT`.

**Проблема:** на каждом срабатывании `dtstart` сдвигается на текущее вхождение, поэтому отсчёт `COUNT` начинается заново. Воспроизведение:
```python
et = datetime(2026,9,22,6,0)
for _ in range(6):
    et = next_occurrence_utc("FREQ=DAILY;COUNT=3", et, "Europe/Moscow", et)
# → 23, 24, 25, 26, 27, 28 — не останавливается
```
Кнопка «Повторить N раз» в конструкторе не работает. Та же причина ломает `INTERVAL` после snooze и quiet-hours, см. A-03.

**Задача для агента:**
1. Хранить неподвижный якорь серии. Добавить в `Reminder` колонку `rrule_dtstart` (naive UTC) через soft-migration в `engine.init_db`. Заполнять её при создании повтора и в `_apply_repeat_change`. Для существующих строк сделать backfill `= execution_time` через `_run_once`.
2. В `next_occurrence_utc` передавать `rrule_dtstart` вместо `execution_time` во всех вызовах. Найти их: `grep -rn next_occurrence_utc bot`.
3. Для `COUNT` второй вариант — считать срабатывания в колонке-счётчике и при достижении N ставить `status="completed"` или `is_recurring=False`. Выбрать один вариант и описать его в docstring.

**Приёмка:** тест «`FREQ=DAILY;COUNT=3`, три срабатывания через `_execute_reminder`, после третьего `next_occurrence` возвращает `None`, джоба не создаётся». Существующие DST-тесты (`test_dst_recurring_reminder.py`, `test_reconcile_dst_next_occurrence.py`) остаются зелёными.

### A-03 · P1 · Snooze повторяющейся (не-привычки) задачи сдвигает её время навсегда

**Где:**
- `bot/handlers/reminders_snooze.py:107-109`;
- `bot/handlers/reminders_shared.py:455-457` — «Своё время» при snooze;
- `bot/handlers/reminders_listing.py:485-486` — «+1ч все».

**Проблема:** защита от дрейфа (не трогать `execution_time`) включена только для `is_habit_like`. У обычной задачи «каждый день в 9» после snooze на час `execution_time` становится 10:00. Дальше `next_occurrence_utc` строит серию от 10:00, и задача навсегда переезжает на 10:00. Проверено: `next_occurrence_utc("FREQ=DAILY", 07:00Z, "Europe/Moscow", …)` даёт `07:00Z` следующего дня, то есть 10:00 MSK.

Второй эффект: snooze после срабатывания перезаписывает джобу `str(id)`, которая уже указывала на завтрашнее вхождение. Сначала сработает snooze, и от него же рассчитается следующее вхождение.

**Задача для агента:**
1. Для **любой** повторяющейся задачи snooze не меняет `execution_time` и `rrule_dtstart`. Нужно только запланировать разовую «snooze-джобу».
2. Snooze-джобу хранить под отдельным id (`snooze_<id>`), чтобы она не затирала джобу следующего вхождения. В `_execute_reminder` различать запуск по snooze (без пересчёта рекуррентности) и регулярное вхождение. Учесть `remove_reminder_job`, `remove_orphan_scheduler_jobs` и `reconcile_jobs_with_db` — они знают только id вида `N` и `nag_N`.
3. Проще после A-02: раз якорь хранится отдельно, snooze может менять `execution_time`, и серия всё равно считается от `rrule_dtstart`.

**Приёмка:** тест «ежедневная задача в 09:00 → fire → snooze 1ч → fire в 10:00 → следующее вхождение завтра в 09:00 локального времени». Аналогичные тесты для «+1ч все» и для snooze через «Своё время».

### A-04 · P2 · `UNTIL` не включает дату окончания; «сегодня» считается по UTC

**Где:** `bot/handlers/reminders_repeat.py:420-436`.

**Проблема:**
- Генерируется `UNTIL=YYYYMMDD`. dateutil понимает это как 00:00 того же дня, поэтому вхождение в 09:00 в последний день отбрасывается. Проверено: для `UNTIL=20260930` серия заканчивается 29.09.
- Проверка «дата в будущем» использует `datetime.now(timezone.utc).date()`, а не локальную дату пользователя.

**Задача для агента:** генерировать `UNTIL=<YYYYMMDD>T235959` по локальному времени пользователя, переведённому в UTC как `...Z`, либо сравнивать по концу локального дня. «Сегодня» брать через `pytz.timezone(user.timezone)`. Поправить `_rrule_end_label`, чтобы он понимал оба формата.

**Приёмка:** тест «до 30.09, ежедневно в 09:00 MSK → последнее вхождение 30.09 09:00».

### A-07 · P1 · MarkdownV2: фильтр по тегу не работает никогда, поиск падает при >25 результатах

**Где:**
- `bot/lexicon/ru.py:141,151`, `en.py:142,152`, `es.py:144,154`;
- используется в `bot/handlers/reminders_listing.py:227-238, 349-356` с `parse_mode="MarkdownV2"`.

**Проблема:** в MarkdownV2 символы `#` и `.` зарезервированы и должны экранироваться:
- `filter_header_tag = "🏷 *#{tag}:*\n"` — неэкранированный `#`, поэтому **каждый** экран фильтра по тегу получает `TelegramBadRequest: can't parse entities`. `safe_edit_text` пробрасывает ошибку дальше, и пользователь видит «Что-то пошло не так».
- `find_truncated_notice = "Показаны первые {shown} из {total}."` — неэкранированная `.`, поэтому `/find` и фильтры с >25 результатами падают.

Скрипт проверки (запускался в аудите) нашёл ровно эти 6 строк:
```python
reserved=set('_*[]()~`>#+-=|{}.!'); # убрать \\. и {placeholders}, оставить * и `
```

**Задача для агента:**
1. Экранировать: `🏷 *\\#{tag}:*\n` и `…из {total}\\.` во всех трёх языках.
2. Добавить тест `test_mdv2_lexicon_keys_are_escaped`. Он проходит по списку ключей, которые рендерятся в MarkdownV2 (`tasks_header`, `tasks_page_indicator`, `find_results_header`, `find_truncated_notice`, `filter_header_*`, `completed_header`, `preview`, `snoozed_until`, `brief_items_more`, `task_done_reply(ies)`), и ищет неэкранированные зарезервированные символы вне `*` и `` ` ``.
3. Для каждого экрана MarkdownV2 добавить fallback: при `can't parse entities` повторить отправку с `parse_mode=None`, как в `daily_briefs._send_safe`.

**Приёмка:** новый тест падает на текущем лексиконе и проходит после исправления. Ручная проверка: тег `#дом` → фильтр открывается.

### A-08 · P2 · «🚫 Не актуально» у повторяющейся задачи пропускает завтрашнее вхождение

### A-09 · P2 · Корректная остановка на деле отменяет уже выполняющиеся задачи

**Где:**

Кроме того, отмена polling-задачи через `task.cancel()` в `_run_until_stopped` обрывает хендлеры, которые обрабатываются прямо сейчас.

**Задача для агента:**
1. Перед `scheduler.shutdown` вызвать `scheduler.pause()`, дождаться завершения выполняющихся задач (`executor._pending_futures`, либо свой реестр задач через обёртку над job-функциями) с таймаутом около 20 с и только потом выполнить `shutdown` и закрыть сессии.
2. Для polling использовать `dp.stop_polling()` (aiogram 3) вместо `cancel()`, чтобы хендлеры завершились штатно.
3. Исправить вводящий в заблуждение комментарий в `__main__.py:519-525`.

**Приёмка:** тест с фейковой job-корутиной, которая спит 0.5 с и затем делает commit: при `stop_event.set()` посередине commit выполнен, `CancelledError` нет.

### A-16 · P2 · ICS-фид: повторяющиеся события дрейфуют при переходе на DST, `UNTIL` невалиден

**Где:** `bot/services/ics_feed.py:58-74`.

**Проблема:**
- `DTSTART:…Z` вместе с `RRULE:FREQ=DAILY`: календарь разворачивает серию в UTC, поэтому после перехода на летнее или зимнее время «09:00» превращается в 08:00 или 10:00. Бот при этом считает серию в локальном времени (`next_occurrence_utc`), и данные расходятся.
- `UNTIL=YYYYMMDD` (тип DATE) при `DTSTART` типа DATE-TIME нарушает RFC 5545 §3.3.10. Часть клиентов (Outlook, Apple) отбрасывает событие.
- Нет `DTEND`/`DURATION` — допустимо, но некоторые клиенты показывают событие на весь день.

**Задача для агента:** генерировать `DTSTART;TZID=<user.timezone>:YYYYMMDDTHHMMSS` с локальным временем и добавить `VTIMEZONE` (или положиться на IANA TZID, который понимает Google). `UNTIL` приводить к UTC date-time. Добавить `DURATION:PT15M`. После A-02 брать `DTSTART` из `rrule_dtstart`.

**Приёмка:** тест парсинга фида через `icalendar` или `dateutil.rrule` для Europe/Berlin: вхождения до и после 25.10 приходятся на 09:00 локального времени.
