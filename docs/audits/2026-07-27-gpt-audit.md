# GPT audit — 27.07.26

Scope: source, tests, deployment files, and project documentation in this
repository. No fixes are included here. Severity is indicative: P0 = data,
security, or core-feature failure; P1 = important user-visible or deployment
failure; P2 = maintainability, coverage, or lower-impact correctness issue.

## Core functional bugs

1. **P0 — Natural-language recurrence is silently ignored.**
    `README.md:23` promises that `каждый день в 9 тренировка` creates a daily
   recurring reminder. `InputParser` returns only a datetime and leaves
   `каждый день` in `clean_text` (`bot/services/parser.py:217-245`); the normal
   save path always calls `create_reminder(..., is_recurring=False)`
   (`bot/handlers/reminders.py:426-437`). The result is a one-off task whose
   title still contains the recurrence phrase.

2. **P1 — Phrases containing hour words can be parsed as the current time
   instead of the requested hour.**
   Dateparser wins before the regex fallback (`bot/services/parser.py:217-224`).
   Reproducible examples include `в 23 часа спать` and `at 14 hours call`, which
   resolve to approximately the current time rather than 23:00/14:00. The
   save path then treats the result as past and asks the user to choose a time,
   instead of honoring the phrase.

3. **P1 — Stale reminder callbacks can mutate a soft-deleted task.**
    `ReminderDAO.get_owned()` checks only ownership (`bot/database/dao/reminder.py:142-155`).
   Done, snooze, edit, settings, and other callbacks use it without rejecting
   `pending_delete_at` rows (for example `bot/handlers/reminders.py:1939-2004`).
   A callback from an old message can therefore complete, reschedule, or edit a
   task during its undo window; cleanup later deletes the mutated row anyway.

4. **P1 — An in-flight scheduler job can still notify a soft-deleted task.**
   `_execute_reminder()` loads reminders by ID and checks status, but never
   checks `pending_delete_at` (`bot/services/scheduler.py:328-358`). The delete
   handler removes the stored job, but cannot cancel a job already running (or
   one that races with deletion), so a task inside its undo window can still be
   sent, rescheduled, and have nagging state updated.

5. **P1 — Deferred-delete cleanup has a time-of-check/time-of-use race with
   Undo.**
   `process_deferred_deletes()` reads a row, checks `pending_delete_at`, then
   deletes events and the reminder in separate statements
   (`bot/services/delete_cleanup.py:46-60`). An Undo can commit between the
   check and delete, yet the cleanup transaction can still remove the row.
   The comment says the re-check is authoritative, but it is not an atomic
   conditional delete/lock.

6. **P1 — Habit motivation statistics count soft-deleted habits as active.**
   The active-habit query in `get_habit_motivation_stats()` has no
   `pending_delete_at IS NULL` predicate (`bot/database/dao/reminder.py:744-759`).
   Deleted habits can inflate active counts, streak maxima, and average scores,
   and can trigger the overload hint.

7. **P1 — Morning brief pins can remain pinned forever.**
   The evening branch unpins only inside `if completed or pending`
   (`bot/services/daily_briefs.py:465-490`). If there is no evening content,
   the morning brief's `pinned_brief_message_id` is never cleared/unpinned.
   This leaves stale content pinned and can interfere with the next morning's
   pin operation.

8. **P1 — `TZ` configuration is effectively unused for users.**
   `Settings.TZ` is only logged (`bot/__main__.py:125`) and is not passed to
   `UserDAO.get_or_create()`; new users default to `UTC`
   (`bot/database/dao/user.py:15-29`). Documentation calls `TZ` the default
   timezone (`README.md:131`), so setting it does not produce the documented
   behavior.

9. **P1 — Telegram payment completion is not validated.**
   `process_successful_payment()` trusts any `successful_payment` and reports
   it as a Stars donation without checking invoice payload, currency, amount,
   or the allowed presets (`bot/handlers/donate.py:99-112`). This is unsafe if
   another payment flow is added and makes the handler's stated donation-only
   contract unenforced.

10. **P1 — The scheduler uses a process-global singleton for all job targets.**
   `SchedulerService.__init__()` overwrites module-global `_instance`
   (`bot/services/scheduler.py:67-72`), while persisted APScheduler jobs call
   the module-level `execute_reminder_job()` (`bot/services/scheduler.py:46-51`).
   Two service instances in one process (tests, embedded apps, or accidental
   duplicate startup) route all jobs through whichever instance initialized
   last; jobs are not owned by their scheduler instance.

## Deployment and security problems

11. **P0 — Docker build context can copy secrets and live databases into the
    image.**
    There is no `.dockerignore`. `Dockerfile:38-39` runs `COPY . .`, while the
    project commonly contains `.env` and `data/` (including SQLite databases).
    `.gitignore` does not affect Docker build context. A build can therefore
    bake bot tokens, user data, and backups into image layers and registries.

12. **P1 — The healthcheck does not restart a hung container.**
    `docker-compose.yml:13-31` defines a heartbeat healthcheck, but Compose's
    `restart: always` restarts only when the process exits; Docker does not
    restart a container merely because its health status is `unhealthy`.
    The comments in `docker-compose.yml` and `bot/__main__.py:50-54` claim the
    check catches a hung polling loop, but no watchdog or orchestrator action
    actually turns that failure into a restart.

13. **P1 — Documented Docker reverse-proxy setup cannot reach the web server
    with the documented defaults.**
    The process binds `127.0.0.1` by default (`bot/config.py:45-58`). Inside a
    container, that is the bot container itself; a reverse proxy in another
    container on the same Docker network cannot connect to it. `DEPLOYMENT.md:238-247`
    recommends exactly that same-network setup without requiring
    `WEB_SERVER_HOST=0.0.0.0`.

14. **P1 — The documented bind mount can be unwritable by the container user.**
    The image runs as UID/GID 1000 (`Dockerfile:11-13,44-45`), but the
    `./data:/app/data` bind mount replaces the image directory's ownership
    (`docker-compose.yml:6-7`). The deployment guide only runs `chmod 755`
    (`DEPLOYMENT.md:58-63`) and does not ensure host UID 1000 ownership or
    group write access. On a root-owned or differently-owned host directory,
    SQLite files and the heartbeat cannot be created or updated, causing
    startup failure or a permanently unhealthy container.

15. **P1 — The optional systemd wrapper does not supervise the container.**
    `DEPLOYMENT.md:152-170` uses `Type=simple` with `ExecStart=docker compose ... up -d`.
    `up -d` exits immediately, so systemd is no longer attached to the service;
    `Restart=on-failure` cannot observe a later container crash, and there is no
    `ExecStop`/foreground `docker compose up` lifecycle.

16. **P1 — Open access is the production default despite security-oriented
    configuration and deployment text.**
    `WhitelistMiddleware` is imported but disabled (`bot/__main__.py:176-185`),
    and `ADMIN_ID` defaults to `0` (`bot/config.py:22-27`). `validate_config()`
    only logs a warning (`bot/config.py:92-113`); it does not fail closed. A
    deployment that omits the whitelist can be used by anyone who discovers
    the bot, with only a per-user in-memory rate limit.

17. **P2 — HTTP rate limiting is proxy-unaware.**
    `bot/services/webserver.py:82-89` keys limits on `request.remote`. Behind a
    reverse proxy all clients may share the proxy's address and throttle one
    another; trusting `X-Forwarded-For` is not implemented either. The intended
    deployment explicitly places the server behind a proxy.

## Test and CI problems

18. **P1 — Utility tests are excluded from the default test command.**
    `pytest.ini:3` restricts `testpaths` to `bot/services bot/keyboards`, but
    `bot/utils/test_time_ext.py` and `bot/utils/test_tags.py` contain 26 tests.
    `pytest --collect-only` collects 348 by default, while `pytest --collect-only
    bot/utils` finds those additional tests. The advertised suite therefore
    does not exercise all repository tests.

19. **P1 — HTTP tests are not runnable in restricted environments.**
    The aiohttp tests bind ephemeral TCP sockets (`bot/services/test_webserver.py`
    and `test_http_rate_limit.py`). In this environment, `pytest -q` produced
    332 passes, 15 setup errors, and one failure with `PermissionError: [Errno 1]
    Operation not permitted`. There is no mark, fixture, or in-process server
    fallback, so CI/sandbox environments that prohibit binds cannot run the
    advertised full suite.

20. **P1 — Documentation claims a nonexistent CI workflow and audit files.**
    `README.md:79,87-89,139-140`, `README.ru.md:79,87-89`, and
    `README.es.md:79,87-89` reference `deploy.yml`, `AUDIT.md`,
    `REWORK_PLAN.md`, and `REWORK_PLAN_2.md`; none exists in the repository.
    `BOT_OVERVIEW.md:268-297` also describes those missing artifacts as present.
    These links and the claim that CI gates deployment are unverifiable/broken.

21. **P1 — Test-count and coverage statements are materially stale.**
    The three READMEs state 135 tests (`README.md:73-79` and equivalents), while
    the current default collection reports 348 tests (and 26 more utility tests
    when explicitly requested). This makes release/quality claims inaccurate.

22. **P1 — ROADMAP describes already-implemented features as missing.**
    `ROADMAP.md:32-41` says repeats are limited to four presets, text time input
    is absent, there are no tags/search/priorities, no progress visualization,
    and no export. The current code contains the repeat builder, manual time
    input, tags/search/priority, Mini App, and data export. Planning decisions
    based on this document will duplicate completed work.

23. **P2 — The documented timezone limitation is obsolete and misleading.**
    README claims onboarding accepts whole-hour offsets only and that
    half-/quarter-hour zones require `.env` configuration
    (`README.md:139-140`). The settings flow now accepts mapped half-/quarter-
    hour offsets such as `+5:30` and `+5:45` (`bot/handlers/settings.py:38-94`).
    Users and operators are given incorrect guidance about supported timezone
    input and the tracked limitation.

24. **P2 — Linting is not clean and is not enforced.**
    `ruff check .` reports 35 errors, including unused imports, unused locals,
    and import-order violations (notably `bot/__main__.py:19,28-44`,
    `bot/config.py:15`, and `bot/handlers/habits.py:26,234`). There is no
    `pyproject.toml`/`ruff.toml` configuration and no present CI workflow to
    gate linting, despite `BOT_OVERVIEW.md:259-262` discussing it.

25. **P2 — The default test bootstrap masks missing required configuration.**
    `conftest.py:3-14` silently injects `BOT_TOKEN=test-token` and an in-memory
    database for all tests. This prevents tests from detecting import/startup
    behavior when required production configuration is absent and can conceal
    configuration regressions.

## Data model, performance, and maintainability problems

26. **P1 — Motivation statistics retain an N+1 event-query pattern.**
    `get_habit_motivation_stats()` loops over every active habit and calls
    `get_events_for_reminder()` (`bot/database/dao/reminder.py:792-798`). The
    Mini App scores path was batched, but the main Habits dashboard still issues
    one unbounded event query per habit on every opening.

27. **P1 — Habit event history and Mini App score reads are unbounded.**
    `get_events_for_reminders()` intentionally loads complete history
    (`bot/database/dao/habit_event.py:136-150`), and scores are recomputed from
    that history for every active habit (`bot/services/webserver.py:177-184`).
    Event rows have no retention/archival policy; long-lived users can cause
    increasingly large responses, memory use, and latency.

28. **P2 — Soft migrations are not a schema-versioned migration system.**
    `init_db()` performs ad-hoc column checks and heuristic backfills
    (`bot/database/engine.py:122-244`). There is no downgrade path, schema
    version validation, migration ordering beyond source order, or portable
    migration tooling for PostgreSQL. Existing malformed data is only warned
    about (`bot/database/engine.py:246-263`).

29. **P2 — Media fields are dead schema.**
    `Reminder.media_file_id` and `media_type` are declared in
    `bot/database/models.py:187-191`, but reminder creation never populates them
    and notification/list/export paths never read or send media. The schema and
    implied feature are misleading and add untested state.

30. **P2 — Habit classification logic is duplicated.**
    The `is_habit_like` predicate exists canonically in
    `bot/database/models.py:424-440` but is repeated in handlers and service
    logic (`bot/handlers/habits.py:57-75` and related imports/branches). A future
    change can make listing, streak accounting, scheduling, and reporting
    disagree about what is a habit.

31. **P2 — Callback payload parsing is inconsistent and can raise uncaught
    exceptions.**
    Several handlers convert callback IDs without a guarded parse, e.g.
    `callback_edit_edit`, `callback_edit_nagging`, `callback_edit_delete`,
    `callback_done_note`, `callback_done_skip_next`, and `callback_snooze_show`
    (`bot/handlers/reminders.py:721-727,1171-1178,1208-1215,2037-2046,
    2081-2091,2193-2197`). Malformed/stale callback data can escape as handler
    errors instead of receiving the standard invalid-action response.

32. **P2 — Language and timezone callback values are not validated against
    supported values.**
    `callback_set_lang()` stores any suffix after `set_lang_`
    (`bot/handlers/commands.py:35-43`), and `callback_set_tz()` stores any
    suffix after `set_tz_` (`bot/handlers/settings.py:345-358`). Generated
    buttons are constrained, but Telegram callback data is client-controlled;
    forged values persist invalid user settings and later force fallback paths.
    In particular, an invalid timezone can make `InputParser._parse_sync()`
    raise from `pytz.timezone()` instead of returning a parse result
    (`bot/services/parser.py:208-224,258-276`), breaking reminder creation.

33. **P2 — Calendar-feed token lookup has no database uniqueness/index.**
    `User.ics_feed_token` is a plain nullable string (`bot/database/models.py:121-129`)
    and `get_by_ics_feed_token()` performs an equality scan
    (`bot/database/dao/user.py:100-105`). Collision probability is negligible
    for the current token length, but the schema does not enforce the stated
    one-token-per-user lookup invariant and performance degrades with users.

34. **P2 — Documentation and implementation disagree on scheduled-job count.**
    README files describe four minute-level cron jobs (`README.md:139`), while
    the composition root registers five feature jobs including deferred-delete
    cleanup (`bot/__main__.py:151-155`), plus heartbeat and cleanup jobs. The
    discrepancy makes operational capacity estimates and monitoring incomplete.

35. **P2 — Repository contains extensive stale “BUG FIX APPLIED” history in
    production docstrings.**
    `bot/config.py:1-10,91-113`, `bot/database/engine.py:103-111`, and many
    handlers embed phase/plan narratives rather than current contracts. These
    comments are contradictory in places (for example open access is both
    warned about and presented as configured security) and increase the chance
    that obsolete assumptions are treated as requirements.

36. **P2 — Database migration code still uses deprecated `datetime.utcnow()`.**
    `bot/database/engine.py:96,239` emits deprecation warnings on current
    Python versions during every migration/backfill. The code will require a
    compatibility update as the deprecated API is removed, and warning noise
    currently obscures real migration failures.
