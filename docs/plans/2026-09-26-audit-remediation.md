# План устранения находок аудита от 26.09.2026

Источник: [docs/audits/2026-09-26-product-and-code-audit.md](../audits/2026-09-26-product-and-code-audit.md), проверенная версия `64c0912`.

Принятые решения владельца:
1. **«Удалить всё»** — сброс данных, а не удаление аккаунта: задачи, события, настройки и ICS-токен удаляются, строка `users` сохраняется со значениями по умолчанию, `payments` не трогаются.
2. **Тихие часы для сводок** (брифы, отчёты) — бесшумная доставка (`disable_notification=True`) внутри тихого окна, а не перенос за его границу.

## Общие правила для каждого шага

- Один шаг — одна ветка и один PR. Ветки: `fix/…`, `ux/…`, `ops/…`.
- Перед PR: `python -m pytest -q`, `ruff check .`, `python3 scripts/scan_secrets.py --no-history`.
- Сначала тест, воспроизводящий проблему и падающий, затем исправление.
- Не рефакторить за пределами шага. Общий код выносить в сервис только когда он нужен в двух местах в рамках текущего шага.
- Если меняется видимое пользователю поведение — обновлять лексиконы (ru/en) и README.

## Этап 1. Корректность и доверие (P1)

### Шаг 1. Сканер секретов не должен сам выводить секрет
Идёт первым — от него зависит надёжность CI для всех следующих PR.
- `scripts/scan_secrets.py:168,178,186`: маскировать совпадение внутри `preview` до формирования результата (заменять найденное совпадение маской в самой строке preview).
- Исключения для примеров применять к конкретному совпадению, а не ко всей строке.
- Тесты:
  - синтетический токен (генерируется в тесте) не встречается ни в stdout, ни в JSON;
  - слово «example» в строке не прячет рядом стоящий настоящий по форме токен.

### Шаг 2. «Удалить всё» при наличии платежа
Места: `bot/handlers/settings.py:619` (`callback_clear_all_confirm`), `bot/database/models.py` (`Payment`), `bot/database/dao/base.py:48`.
- Новый метод, например `UserDataService.reset(user_id)`, выполняющий удаление задач, событий, настроек и ICS-токена одной транзакцией; `payments` не трогать.
- Порядок: транзакция → commit → снятие jobs у планировщика → сообщение пользователю. Если commit не прошёл — jobs не трогать, показать ошибку/`db_busy`.
- После сброса пользователь проходит онбординг (язык, пояс) заново, как сейчас.
- Текст подтверждения: явно указать, что история платежей сохраняется для поддержки (`/paysupport`).
- Тесты:
  - «платёж → задача → привычка с событиями → сброс» проходит успешно, запись платежа на месте;
  - отказ commit оставляет задачи и jobs нетронутыми (нет рассогласования БД/планировщика).

### Шаг 3. Единая обработка результата парсера + убрать «Уверенность: N%»
Места: `bot/handlers/reminders_wizard.py:201`, `bot/handlers/reminders_shared.py:464`, `bot/services/parser.py:407`, `bot/lexicon/ru.py:325`.
- Выделить в `reminders_shared.py` один маршрутизатор результата парсера (сохранить / спросить час / спросить заново), используемый созданием, ручным вводом (`state_choosing_time_text_input`) и изменением времени.
- Если день распознан, а час нет — спрашивать только час, сохраняя распознанную дату в FSM. Быстрые кнопки времени строить от этой даты, а не от сегодня/завтра.
- Заменить «Уверенность: N%» объяснением недостающей информации («Понедельник понял. Во сколько напомнить?»); число оставить только в логах/диагностике.
- Тесты:
  - «в понедельник» при ручном вводе → вопрос про час, не немедленное сохранение;
  - «в понедельник» → кнопка «09:00» → задача на понедельник 09:00 в поясе пользователя;
  - тот же сценарий при изменении времени существующей задачи.

### Шаг 4. Действия после сохранения задачи
Места: `bot/handlers/reminders_shared.py:647`, `bot/keyboards/inline.py:163`, `bot/handlers/commands.py:81`.
- После commit показывать компактную карточку «✅ текст — дата/время» с кнопками «Изменить», «Удалить», «Закрыть».
- «Закрыть» только скрывает клавиатуру. «Удалить» использует существующий механизм удаления с возможностью отмены.
- `cancel_wizard` оставить только для экранов до сохранения задачи.
- Убрать автоматическое скрытие клавиатуры через 5 секунд.
- Тесты:
  - после сохранения на клавиатуре нет `cancel_wizard`;
  - «Удалить» снимает job и удаляет задачу; «отменить удаление» восстанавливает и задачу, и job.

### Шаг 5. Единая политика тихих часов
Места: `bot/services/daily_briefs.py:351`, `bot/services/habit_reports.py:305`, `bot/database/models.py:130`.
- Единая функция, например `notification_policy(user, kind, now) -> deliver | silent`, в `bot/services/`, используемая напоминаниями, брифами, отчётами и восстановлением пропущенного.
- Внутри тихого окна сводки (брифы, отчёты) доставляются с `disable_notification=True`, а не переносятся; обычные напоминания продолжают переноситься/подавляться как сейчас.
- В настройках тихих часов — одна строка: «Сводки в это время приходят без звука».
- Исправить README, где обещано «подавление всех уведомлений».
- Тест: параметризованный по типу сообщения (напоминание, бриф, отчёт, восстановление), окно 23:00–07:00, время отправки 23:30 → ни одного вызова `send*` без `disable_notification=True` для сводок; поведение обычных напоминаний не меняется.

## Этап 2. Эксплуатация

### Шаг 6. Надёжный деплой
Место: `.github/workflows/deploy.yml`.
- `set -euo pipefail` в скрипте деплоя.
- Деплоить проверенный SHA (`git fetch && git checkout --detach ${{ github.sha }}`), а не `git pull`.
- Бэкап делает деплой блокирующим: ошибка бэкапа прерывает деплой (сейчас best-effort).
- После `docker compose up` — проверка готовности (healthcheck контейнера или HTTP-проверка Mini App), при провале — откат на предыдущий SHA.
- Добавить `scripts/verify_backup.sh`: восстанавливает последний бэкап во временную БД, выполняет `PRAGMA integrity_check` и `SELECT count(*)` по основным таблицам; запускать сразу после бэкапа.
- Ручная проверка на VPS выполняется владельцем, агент готовит только PR.

### Шаг 7. Тексты и первый запуск
- В онбординге после выбора языка и пояса показывать пример: «Напиши: завтра в 10 позвонить маме». Первая созданная задача завершает знакомство.

### Шаг 9. Группировка настроек и разбиение `settings.py`

### Шаг 10. Локализация Mini App

## Что сознательно не включено

| Пункт | Почему |
|---|---|
| Отдельный рефакторинг «сервис операций над задачей» | Складывается по ходу шагов 2–4 (транзакция → commit → jobs). Отдельный рефакторинг рискован и не даёт пользователю ничего немедленно. |
| Разбиение `scheduler.py` и `ReminderDAO` | Пока нет конкретной боли. Вернуться, когда шаги 5 и 13 упрутся в эти модули. |
| `next_*_at`, PostgreSQL, полное версионирование схемы | Аудит сам рекомендует сначала измерить (длительность cron-циклов, задержки, блокировки). Максимум — залогировать длительность циклов. |
| Предупреждение о дубле, «умный» перенос из истории | Мало пользы на единицу сложности; вернуться при реальных жалобах пользователей. |
| Голосовой ввод | Стоимость распознавания, хранение аудио, новая точка отказа. Только после этапов 1–3 и при наличии спроса. |
| Продуктовые метрики (время до первой задачи, доля уточнений и т.п.) | Полезны, но отдельная задача: сначала нужно решить, где их хранить без записи текста задач. |
| Ротация ранее раскрытого токена (аудит от 22.09) | Ручное действие владельца вне кода, не для агента. Статус нужно закрыть отдельно. |
